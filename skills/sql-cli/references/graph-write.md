# 写回业务语义

读代码（实体类、Mapper XML、`.sql`、注释、常量表）得到的表/字段含义、JOIN 关系和字段血缘，
是图谱的重要补充来源——**数据库元数据导入拿不到这些**。发现了就写回去，不要只放在回答里。

## 四个描述字段，各写各的

这是最容易写错的地方。**写错不会报错，只会让下次查询更难。**

| 字段 | 装什么 | 长度 | 谁写 |
|---|---|---|---|
| `comment` | **数据库注释**——库里 `COMMENT` 的镜像 | 库里多长算多长 | **只有 `schema import`。你不能写，也不该想办法写** |
| `--business-name` | **业务名**——短标签，检索键 | 一个词到一个短语 | 人 / Agent |
| `--description` | **业务描述**——口径、坑、来源、注意事项 | 一段话 | 人 / Agent |
| `--semantic-type` | **语义类型**——固定枚举 | 枚举值 | 人 / Agent |

**判据：能不能塞进查询结果的列头。** 查询结果的列头会在裸列名下面加一行 `businessName`，
「买家」放得下，「下单用户 ID，软删除的用户仍保留在此」放不下——后者写 `--description`。

**库注释是错的怎么办？** 两件事一起做，缺一不可：

1. **告诉用户去数据库里改，然后重新导入。** 这是唯一能真正修好 `comment` 的路径，
   而这个权力不在你手上——不要去改 `comment`，也不要试图绕过。
2. **同时把正确的业务含义写进 `--description`。** 这不是绕过，是 `description` 这个字段的
   正当用途：两者会并排显示，冲突一眼可见，反而在提醒人去库里修。

真正不该做的只有一种：**只写 `--description` 却不告诉用户库注释有问题**——
那等于用一句对的话盖住一句错的话，人再也不会去修源头了。

**`--semantic-type` 必须用枚举值，不要写自由文本。** 规则引擎（`PolicyEvaluator` 的
`semanticTypeAny`）和搜索加权都靠精确匹配。写「手机号」而不是 `phone`，等于没写，
一条规则都命中不了。合法取值见 `schema edit --help`。

## 术语：一个词对应多个落点时才建

`add-term` 是最容易被滥用的命令——建一条看起来和写一个 `--business-name` 一样便宜，
实际上多一个要维护的对象，还占着搜索的最高权重档。

**判据是基数，不是重要程度：**

| | 挂在哪 | 基数 | 回答的问题 |
|---|---|---|---|
| `--business-name` | 对象自己身上 | 1 : 1 | 「这张表 / 这个字段叫什么」 |
| `add-term` | 独立对象 + 映射边 | **1 : N** | 「这个词对应哪些表和字段」 |

术语一般是**业务核心概念**，天然横跨多张表和多个字段。三种情况下它不可替代：

1. **一词多物**——「巡检计划」对应三张表（计划主表 / 点位配置 / 点位实例），
   `--business-name` 只能挂在其中一张上
2. **多词一物**——表和字段**没有** `aliases` 字段，只有术语有。同义词没有第二个地方放
3. **定义无处安放**——一句定义不提任何具体的表就说得清（「报事：住户提交的一次维修请求」），
   它属于术语；必须提到某张表才说得清的，那是那个字段的 `--description`

**先停下来想想要不要建：**

- 只映射到**一个**字段、**又没有同义词** → 等价于把这个词写进那个字段的 `--business-name`，
  而且更省。这种情况就别建
- 这个词在**前端面客的代码里几乎不出现** → 多半是开发内部叫法，不是业务词汇

```bash
# 这条成立：只映射一张表，但「工单 / 报修 / 报事单」三个同义词只有术语放得下
sql-cli <alias> schema add-term 报事 --display-name "报事"   --aliases "工单,报修,报事单" --map <schema>.erp_prop_report
```

### 场景：给了 `--primary-target` 的术语能直接展开成子图

术语默认只回答「这个词对应哪些表」。给它一个**入口表**，它就升级成场景，
搜索命中时直接给出**这件事要用哪些表、怎么连、要带哪些过滤**：

```bash
sql-cli <alias> schema add-term 报事 --display-name "报事"   --aliases "工单,报修,报事单" --description "住户提交的一次维修请求"   --map <schema>.erp_prop_report,<schema>.erp_prop_report_assign   --primary-target <schema>.erp_prop_report   --filter "state IN (0,1,6)" --filter "subject_id = :subjectId"
```

**`--primary-target` 指向什么决定行为**：指向一张表 → 能展开子图；指向列或不给 →
就是今天的同义词路由。不用声明「这是不是场景」，指向本身就是答案。

**场景粒度 = 一个前端页面能完成的事**（报事列表页、派单页、回访页各是一个），
不是一个业务域。「报事域有 20 张表」这种粒度又退回只给点不给边。

### `--filter` 只放场景专属的条件

判据是**换一个场景这条还成不成立**：

| 条件 | 进不进 `--filter` | 为什么 |
|---|---|---|
| `state IN (0,1,6)` | **进** | 换成回访场景就得是 `IN (6,7)` |
| `is_nock = 1 AND state = 0`（可抢单） | **进** | 同上 |
| `subject_id = :subjectId` | **进**，占位符形式 | 值运行时给，但**位置必须有**——漏掉项目隔离列不是多查几行，是**查到别的项目的数据** |
| `del_flag = 0` | **不进** | 换任何场景都成立，是全库约定，走 policy 规则 |

一个条件一个 `--filter`，不要用逗号拼——条件里本来就有逗号。
**它是整体替换不是追加**：一组条件要共同成立，追加会把上次写错的永久留下；
不给 `--filter` 就不动原有的。

**写错 `--filter` 是这一节最贵的错**：`state` 的完整值域是
`0派单中 1处理中 2已处理 3已取消 4派单超时 5处理超时 6回访中 7回访完成`，
「未完结」写成 `IN (0,1,6)` 就漏掉了两种超时——而超时的单恰恰最该被看见。
**SQL 照跑、有结果、少的那批没有任何迹象。** 拿不准就先不写。

### 空壳术语写不进去

**不带 `--map` 也不带 `--aliases` 会被直接拒收（退出码 1）——即使给了 `--description`。**
判据只看这两样：术语要么挂 ≥2 个对象（一词多物），要么有同义词（多词一物）；
两者都没有的话，这条术语跟 `--business-name` 完全重叠，而且更差——多一个对象要维护，
还占着检索的最高权重档。`--primary-target` 指向图谱里不存在的对象同样硬拒。

**只写了 `--description` 撞上这条闸门怎么办：改用 `schema edit --business-name`。**
报错会直接给出可粘贴的命令（`schema edit --table <schema.table> --business-name "<词>"` /
`--column ...`），把词填进对象自己的业务名，不要因为报错就放弃写这条语义。

**`--negative-aliases`：挡跨域撞词。** 同一个词在不同业务域可能指完全不同的东西——
「扫码」在巡检域是点位打卡，但「扫码打卡」在考勤域另有所指。查询恰好等于某条负向词时，
这条术语这次**整个不参与匹配**（不影响它被其他查询正常命中）：

```bash
sql-cli <alias> schema add-term 扫码 --description "巡检点位打卡扫码，不是考勤打卡" \
    --map <schema>.erp_prop_task_plan.is_scan,<schema>.erp_prop_plan_point.start_time \
    --negative-aliases "扫码打卡"
```

### 术语从哪来：前端面客的文案为主，后端为辅

**术语是用户嘴里的词，不是开发嘴里的词。**

| 来源 | 权重 | 为什么 |
|---|---|---|
| **前端面客处**——表单 label、表格列头、菜单名、筛选项、提示文案 | **主** | 业务方和客户实际在用的说法。同义词也大多在这里：同一个概念在不同页面叫法不同，那就是天然的 `--aliases` |
| 后端实体类注释、常量类、Mapper | 辅 | 用来确认这个词落在哪些表和字段上，不是用来发现词 |
| 库注释 | 辅 | 同上，而且经常过期 |

只从后端往回找会建出一堆**只有开发认识的词**（`bizType`、`dataSource`、`delFlag`），
用户不会那样提问，这种术语对 agent 理解业务没有任何帮助。

**顺序：先在前端找到这个词和它的各种叫法 → 再到后端确认它落在哪些表 / 字段 →
一次 `add-term` 把 `--aliases` 和全部 `--map` 带齐。** 分几次补容易漏掉映射，
而一条只有名字没有落点的术语，搜索命中了也带不出任何表。

## 字段值域（对查询正确率影响最大的一块）

不知道 `status` 的 `1` 是「已付款」还是「已发货」时，猜出来的 SQL
**有结果、不报错、答案是错的**——这种错没人看得出来。所以读表时顺手把值域补上。

四选一，具体写法见 `schema edit --help`：值能穷举用 `--enum-values`（`0=待付款` 形式，
含义不知道就只写值）；值多且来自字典表**不要内联**，改建一条指向字典表的关系；
值无限但有格式用 `--format`；都不是就 `--example` 追加真实值。

值从哪来，按成本排序：**列注释**（中文库里状态字段的注释十有八九就写着 `0-待付款 1-已付款`，
`describe --json` 里已经有了，直接抄，这是主力）→ **代码**（枚举类、常量类、Mapper XML）
→ **字典表** → **`schema value-domain` 兜底**，见下。

### 别自己拼采样 SQL：`schema value-domain` 已经把三个来源交叉好了

```bash
sql-cli <alias> schema value-domain --table app.orders          # 整表扫，高基数列自动跳过
sql-cli <alias> schema value-domain --table app.orders --column status     --code-enum '0=待付款,1=已付款,2=已发货' --basis 'OrderStatus 枚举类'
```

交叉的是**库里的实际分布 × 字段注释 × 代码枚举**。前两个它自己取，第三个只有你能给——
CLI 读不到代码。四种结论里最要紧的是「**库里有、注释和代码都没声明**」：
注释过期或有脏数据，而这正是会让你写错 `WHERE` 的那种。另有一种只有它看得出来：
**全 NULL 或只有一个取值 = 这个字段实际没在用**，别拿它做判断。

- **给了 `--code-enum` 就必须给 `--basis`**：一句话交代这份枚举从哪读来的（哪个类 / 哪个文件）。
  审批人看不到你读的代码，不说来源他只能盲批或盲拒
- **它产出的是审批，不是写入**，而且无条件排队，跟别名的 `approveGraph` 开关无关。
  一次采样看不到的值它不知道，直接写意味着一次剖析就改掉几十个字段的值域

不用做全量普查——**只补这次真要查的表**，而且只有状态/类型/标志/编码类字段需要。

## 候选机制：哪些要人发布，哪些直接生效

**这两类的风险完全不同，要区别对待。**

| 命令 | 状态 | 后果 |
|---|---|---|
| `add-relation` / `add-term` / `add-lineage` / `add-metric` | **候选**（`candidate`） | 已写进图谱但不算正式，同时排一条审批进**评审页 · 待审批**。批准 = 发布定级，拒绝 = 转「已忽略」 |
| `remove-lineage`（`--target [--through]` 或 `--id`） | **删除**，走同一条管线 | `manual` 别名上排成审批，批准才真删。写错的血缘用它删，不要用另一条去「盖」 |
| `schema edit`（描述、业务名、语义类型、值域、`--redundant-of`） | **立刻生效，标着未确认** | 值马上能被检索和查询用上，但 `describe` 会标 `[待确认]`，工作台看板有「字段语义待确认」计数 |

所以**写字段语义要比写关系更谨慎**。这反直觉，但确实如此：候选是"写进去了还不算数"，
而字段语义是"算数了，只是没人认过"——中间没有人工放行这一步拦着。

字段语义没有候选态是有意的（标量值没有"不生效的值"这回事），闸门是 `verified` 位：
**你写的一律未确认**，人在 Web UI 的字段编辑里改过才算确认。人确认过的字段你又改了值，
之前那次确认自动作废——所以别为了"顺手统一格式"去覆盖已经确认过的字段。

**别名是 `graphApproval: manual` 时上面这张表整个失效**：两类写入都变成
「先落运行库、批准后才写图谱」，命令立刻返回 `待审批（审批 #N）` 而图谱一个字节没动。
退出码 0 不等于生效，见 [troubleshooting.md](troubleshooting.md) 的「审批：一条管线，两个结尾」。

候选写完立刻能被 `search` 和 `describe` 看到，**默认包含但明确标注**：
`search` 结果带 `candidate: true`（文本是 `[候选]`），`describe` 的候选关系带 `[候选]` 前缀，
`stats` 有 `candidateRelations` / `candidateTerms` 计数。**搜得到不等于已发布，看标记。**

**被人拒绝过的候选会留下 `[已忽略]` 标记而不是消失。** 看到这个标记说明有人明确否定过它——
不要重新提交同一条，除非你有新证据，并在说明里写清新证据是什么。

## 什么时候开批次

判据、两种 `--kind`、命令序列和三条纪律统一写在
[SKILL.md · 批次](../SKILL.md#批次多条改动作为一个业务意图)，这里不再复制。
图谱侧只提醒一句：**按一张表的语义做整表补全**、**读一遍代码补一个业务域的 N 个字段和关系**
该开批次；会话里顺手补的两处不相干改动、一次 `schema import`，不该。

## 关系类型只有三个

按谁维护划分，完整说明见 `schema add-relation --help`：

| type | 用途 | 最低 confidence |
|---|---|---|
| `join_observed` | 人和 Agent 维护的表间关联，column → column。**你能建的基本只有它** | 0.5，**必须显式传** |
| `term_mapping` | 术语 → 表/字段，一般由 `add-term --map` 创建 | 0.5 |
| `foreign_key` | 数据库声明的外键，只由导入产生，**不要手工创建** | 1.0 |

**只有这三个**，别的类型名一律不认。

**关系的语义靠 `--join` 表达，不靠类型名**——推断的外键、代码里看到的 JOIN、
字段取值来自字典表，都是 `join_observed` 加一个说清楚条件的 join 表达式。

字段取值来自字典表时，join 表达式里**必须带上字典的过滤条件**，
否则顺着这条边查字典会捞出全表：

```bash
sql-cli <alias> schema add-relation --type join_observed \
  --from qm_pct.orders.status --to sys_dict.dict_item.dict_key \
  --join "orders.status = dict_item.dict_key AND dict_item.dict_type = 'order_status'" \
  --confidence 0.9
```

## 置信度规则（CLI 强制校验，违反直接退出码 1）

- **`join_observed` 必须显式传 `--confidence`。** 它是推断类关系，没有默认值兜底，
  漏传直接被拒绝，工作区不会有任何改动。
- **`--verified` 要求 `--confidence >= 0.9`。** verified 表示「人已核对过」。
  只有从数据库外键约束、明确的实体注解，或你实际 `describe` 过两端字段确认语义一致，
  才配得上。**读起来像的 JOIN 不要标。**
- `--confidence` 只接受 0.0~1.0，低于该类型最低值会被拒绝。

取值参考：明确外键语义 0.9~1.0；同名同义且业务语义清楚 0.75~0.85；
代码里观察到但含动态条件 0.6~0.7；仅字段名相似 0.5。

## 冗余副本与权威来源

宽表里的 `orders.customer_name` 常常是下单那一刻的快照，权威源在 `customer.name`。
Agent 检索到哪个用哪个，可能拿到历史快照而不是当前值——**又一个静默错误**。

发现这种情况用 `schema edit --column <ref> --redundant-of <权威列>` 标注，
`search` 命中这一列时会带出提示。

**边界：不做规范化建议。** 不要说「这张表不满足 3NF，建议拆分」——那是设计期的事，
不是这个工具的场。只标注权威源在哪。

## 少而准

一次会话里**只写回这次真正用到并验证过的知识**。理由：

- 候选要人一条条评审，写得多而准确率低，等于把成本转嫁给人
- 写错的语义会误导之后所有查询，而且**没人会主动来复核**

confidence 不够就**不写**，不要降标准硬塞。写图谱的命令失败时看 stderr 的具体原因。

**编辑或导入之后跑一次 `schema index rebuild`**，否则 `search` 搜不到新写的东西。

## `schema eval` 给你一份工作队列

```bash
sql-cli demo schema eval          # 硬错误 + 覆盖率；硬错误 > 0 时退出码 1
sql-cli demo schema eval --json   # findings[].remediation 里就是要执行的命令
```

**什么时候跑**：写完一批图谱之后自检一次。它不连数据库、不改图谱，跑它没有副作用。

**怎么读**：报告只有两部分，判读方式完全不同。

| 部分 | 判读 |
|---|---|
| **硬错误**（`term.orphan` / `desc.dead-ref` / `rel.endpoint-mismatch`） | 「无论如何都是错」，**必须清零**，非 0 时退出码就是 1 |
| **覆盖率**（表描述 / 列描述 / 列值域 / 术语有映射） | 只报告，**没有阈值**。低不代表要立刻去补——按需生长的图谱任何时刻都是部分完整的 |

**finding 里的命令直接执行**——那是它存在的全部理由。带 `<…>` 占位的地方换成你的判断，
其余原样粘：

```
[error] term.orphan term:demo:工单
    术语「工单」既没有描述也没有映射目标，检索会让它占住 Top1 却给不出任何落点
    修：sql-cli demo schema add-term 工单 --description '<这个词在业务上指什么>' --map <schema.table>
```

`term.orphan` 是三条里最要紧的：空壳术语不是「少了点东西」而是**主动有害**——
术语在检索里权重最高，一条没有内容的术语稳稳占住 Top1，把真表压下去
（实测 5 条空壳让 Top1 从 55.6% 掉到 11.1%）。所以**别为了「先占个位」建术语**。

**看到「产出 N 条，超过闸门 50」不要逐条修**：那条 finding 说的是这个探针用错了对象。
先拿它给的样例验证判断，别拿一份没人做得完的清单当任务。

结果落运行库并绑当前 revision，改完重跑就能比对两次。

## 重构前先跑 `data-quality`

改一张表之前，**代码永远回答不了这三句**——代码只能说有没有人写这行，不能说这行还跑不跑：

> 这个字段能删吗 · 这个枚举值还有人写吗 · 这张表还活着吗

只有库能回答。

```bash
sql-cli demo schema data-quality --table app.orders --yes            # 不给 --yes 会先列出要跑的查询
sql-cli demo schema data-quality --table app.orders --months 6 --yes # 「多久没写入算死」的窗口
sql-cli demo schema data-quality --table app.orders --yes --json     # findings[].remediation 直接执行
```

**它连库**，跑的是只读聚合（默认只采 10000 行）。这是它和 `schema eval` 唯一的区别，
也是不能合并的理由：`eval` 是纯计算随便跑，这条要往库上打几百条查询。
不给 `--yes` 时它会把**将要执行的每一条 SQL** 打出来然后退出——
那份清单就是要你确认的东西，**照着 CLAUDE.md 的授权要求，先给用户看再加 `--yes` 重跑**。

四条探针，前三条改的是你的判断，最后一条改的是你写不写 JOIN：

| 探针 | 它在说什么 | 你该怎么做 |
|---|---|---|
| `data.column-unused` | 整列全 NULL，或 99% 的非空值是同一个取值 | **别拿它做判断**，也别拿它当筛选条件。确认是废弃还是本环境没数据后按 finding 给的命令标注 |
| `data.enum-undeclared`（**error**） | 库里有图谱 `enumValues` 之外的取值 | 你按图谱写的 `WHERE status IN (...)` **会静默漏掉这批行**。先补值域再写 SQL |
| `data.orphan-fk` | 这条已验证的外键，from 端有一批值在对端找不到 | 按它写 `INNER JOIN` 会**丢掉这批行**。要么改 `LEFT JOIN`，要么先查清这批孤儿是什么 |
| `data.table-dead` | 行数为 0，或最后一次写入超过 N 个月 | 这张表可能已经被取代了。别在它上面继续加东西，先确认还有没有写入方 |

## 规则：从存量表归纳出来，提议给人

读了十几张表发现「每张都有 `create_time` / `update_time`，都是 datetime NOT NULL」，这不是
一条条写进表描述的事——它是**全库约定**，写成规则后新表自动适用，建表时被拦。

```bash
sql-cli demo schema policy rule add --category required_business_columns \
  --reason "抽查 t_order/t_user/t_bill 等 12 张业务表，全部带 create_time/update_time datetime NOT NULL" \
  --column "created_at datetime notnull comment=创建时间" \
  --column "updated_at datetime notnull comment=更新时间"
```

- `--reason` **必填且要写来源**：人在待审批队列里裁决的就是这句话。「维护规则」等于没写
- `--column` 写法：`name [类型] [notnull] [default=X] [comment=X]`。**字段名必须完全一致，
  没有别名**：存量库里 `create_time` / `gmt_create` 混用正是要靠这条规则终结的，规则里写
  「叫哪个都行」等于把不统一写进规则。挑一个名字提，别的写法就是违规
- 默认 `--enforcement advisory`：先只提示一段时间，人看过几次提示确认没误伤再在规则页升成 `required`
- 走别名的 `graphApproval`：`manual` 进评审页待审批，批准才写入并启用；`auto` 当场生效并留底
- 目前只有 `required_business_columns` 能从 CLI 提议，其余类别在规则页配置

提议之后**不要自己去绑定或改规则文件**，也不用在建表前先跑评审：规则启用后
`CREATE / ALTER / DROP` 经过 `sql-cli` 执行时自动检查，被拒的错误里带修法，照改再执行。

**什么时候跑**：重构、下线字段、清理旧表之前跑一次；日常查数不用跑。
它不改图谱（只提议 `schema edit` 命令，要你自己判断后执行），结果落
`graph_evaluation`（`source=data-quality`）——和 `schema eval` 同一张表，但**没有覆盖率指标**，
数据层没有「覆盖了百分之多少」这回事。
