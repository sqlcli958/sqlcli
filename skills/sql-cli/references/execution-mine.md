# 从执行记录回溯

每次通过 `sql-cli` 执行的 SQL 都被记录下来了。**已经跑通过的写法，比你现推的可靠**——
它至少证明了：表名对、字段名对、JOIN 条件成立、权限够。

## 唯一的入口：`describe` 的 `recentSql`

```bash
sql-cli <alias> schema describe <schema.table> --json
```

返回里的 `recentSql` 是**这张表最近的成功查询范例**（脱敏后的真实 SQL，最多 5 条）。

**在自己拼 SQL 之前先看它。** 尤其是这几种情况，它能直接省掉一轮试错：

- 这张表的**软删除约定**（`AND deleted = 0` 这类几乎不会写在注释里的隐含条件）
- 这张表实际被怎么 JOIN（可能和图谱里记的关系不完全一致）
- 时间字段用的是哪一个（`created_at` 还是 `pay_time`）
- 状态值的真实形态（`status = 1` 还是 `status = '1'`）

> 目前没有浏览完整执行历史的 CLI 命令，`recentSql` 是 Agent 能拿到的全部。
> 更全的执行记录在 Web UI 的评审页「执行记录」标签里，那是给人看的。

## 从 `recentSql` 里提炼知识写回图谱

看到反复出现的模式就写回去，这是**成本最低的一类图谱补充**——不用读代码，不用连库，
`describe` 一次就有了。

| 你在 `recentSql` 里看到 | 写回什么 |
|---|---|
| 反复出现的 JOIN 条件，而图谱里没有这条关系 | `add-relation --type join_observed --join "<完整条件>"` |
| 反复出现的隐含过滤（`deleted = 0`、`tenant_id = ?`） | `schema edit --column <ref> --description` 写明这个约定 |
| `WHERE status = 2` 而图谱值域里没有 `2` | 值域标注不全，补 `--enum-values`（**含义未知就只写值，不要猜**） |
| 同一个业务概念反复用某几张表 | `add-term` 建术语并 `--map` 到这些表 |

## 三条必须守住的约束

**1. 执行记录里的 SQL 不都是对的。**
它只证明「跑通了」，不证明「业务上正确」。一条 JOIN 少写了租户条件照样能跑通，
只是数错了。所以：**看到就当线索，不当结论**。

**2. 幸存者偏差。**
`recentSql` 只有 5 条，而且是**已经有人查过的**那些。它能告诉你「这么写可行」，
**不能告诉你「这是唯一或最好的写法」**，更不能用来判断关系的完备性。
不要因为 `recentSql` 里没出现某张表就认为它无关。

**3. 加权判断，不要见一条写一条。**
按 **出现频次 × 是否成功** 判断。5 条里出现 1 次的 JOIN 是弱信号，
confidence 给 0.6 左右并在 `--join` 里说明来源是执行记录；
5 条里出现 4 次的才配得上 0.8 以上。**任何情况下都不要给 `--verified`**——
从执行记录推出来的东西没有人核对过，不符合 verified 的定义（见 [graph-write.md](graph-write.md)）。

## 别把字面量带进图谱

`recentSql` 是脱敏后的，但你仍然可能看到 `status = 2`、`tenant_id = 1001` 这类值。

- **可以**记录「这个列的取值形态是整数、见过 2」
- **不要**把具体的业务主键、账号、手机号写进图谱的任何字段——
  即使它在脱敏后侥幸留下来了
- 敏感语义类型（`phone` / `id_card` / `bank_card` / `email` / `person_name` /
  `address` / `account`）的列，**一律不要记录样例值**
