# 图谱语义机制的分工，与「术语」该是什么

> 类型：**设计讨论记录**，不是执行清单。结论落到条目请进
> [dev-checklist-2026-09](dev-checklist-2026-09.zh-CN.md)。
>
> 起因：2026-08-27 检查 agent 写进 `erp_plush_test` 的 5 条业务术语，发现全部是空壳
> （无 `description`、无 `--map`、全库 0 条 `term_mapping` 边），而且**主动有害**——
> 术语在检索里权重最高（`WorkspaceIndexedSearchEngine` 给 term 8 分档），空壳术语稳稳占住
> Top1 把真表压低一名。9 个 case 实测：Top1 从 55.6% 掉到 11.1%，MRR 从 0.66 掉到 0.41。
>
> 但真正的问题不是那 5 条数据，是**「术语」和「业务名」的边界从来没定义过**，
> 于是它在实践中退化成了重复堆功能。本文是把边界定下来的过程和结论。
>
> **当前状态：方案 C 待拍板，未动手。**

---

## 一、判据

> **一个语义机制存在的理由 = 它能回答别的机制回答不了的问题。回答不了就删，重叠就合并。**

这条判据是本文所有结论的唯一来源。下面每一节都是拿它去过一遍。

---

## 二、六个机制过一遍

图谱里做「把人说的词翻译成库里的位置」这件事的，一共六个机制。逐个问「能不能被别的替代」：

| 机制 | 能被替代吗 | 结论 |
|---|---|---|
| `comment`（DB 注释镜像） | 不能——唯一**不是人写的**事实来源，导入免费拿到 | 保留 |
| `businessName` | 不能——**1:1 场景的正确形态**。用术语替代意味着 10114 个字段要建 10114 个术语对象 | 保留 |
| `description` | 不能——说的是「这个数据位置怎么回事」，绑定具体字段 | 保留 |
| `semanticType` | 不能——**机器可判定的类型**（该脱敏、该按手机号处理），不是自由文本 | 保留 |
| `metric` | 不能——口径，跟检索是两件事 | 保留 |
| `term` + `term_mapping` | **在「1:1 且无同义词」时与 businessName 完全重叠** | 问题在这 |

**结论：不是六个机制互相重复，是一个机制被用在了它不该用的场景。**

### 2.1 术语与业务名的边界：在基数，不在语义

| | 挂在哪 | 基数 | 回答的问题 |
|---|---|---|---|
| `businessName` | 对象自己身上 | **1 : 1** | 「我有个表，它叫什么」 |
| `term` | 独立对象 + 映射边 | **1 : N** | 「我有个词，它对应哪些对象」 |

**一个只挂 1 个对象、又没有同义词的术语，完全等价于把那个词写进 `businessName`，而且更差**——
多一个对象要维护，还占着检索的最高权重档。

术语只在三种情况下不可替代，而这三种 `businessName` 都办不到：

1. **一词多物** —— 「巡检计划」在 ERP 里对应三张表（`erp_prop_task_plan` 计划主表 /
   `erp_prop_task_point` 计划点位配置 / `erp_prop_plan_point` 任务点位实例）。
   `businessName` 只能挂在其中一张上。
2. **多词一物（同义词）** —— 已核实：**表和字段根本没有 `aliases` 字段**，
   只有 `TermWorkspaceNode` 和 `MetricRecord` 有。同义词除了术语没有第二个地方放。
3. **负向词** —— `negativeAliases` 也是术语独有。「扫码」的别名「扫码打卡」会把查询引到
   考勤域（`erp_shift_*`），只有术语能挡。

**这条判据还缺一半：满足基数只说明「可以有」，不说明「值得有」。**
补一条来源判据——**术语是用户嘴里的词，不是开发嘴里的词**，所以它的第一来源是
**前端面客的文案**（表单 label、表格列头、菜单名、筛选项），后端实体注释和库注释只是辅助，
用来确认这个词落在哪些表 / 字段上，不用来发现词。

只从后端往回找会建出一堆只有开发认识的词（`bizType`、`dataSource`、`delFlag`）——
它们基数上也可能是 1:N，但用户不会那样提问，检索永远命中不到，占着最高权重档白占。
反过来，同一个概念在不同页面上的不同叫法，就是天然的 `aliases`——那也只有前端才看得到。

配套的一条负判据：**只映射一个字段、又没有同义词，就不该建**（等价于 `businessName` 且更省）；
**在前端几乎不出现的词**同理。这两条已写进技能
[graph-write.md](../skills/sql-cli/references/graph-write.md) 的「术语」一节。

### 2.2 术语的 description 与字段的 description：对象不同，不是详略之分

- `column.description` 描述**一个数据位置**：「扫码动作写入 scanPoint，为空表示该点位尚未扫码」
  —— 离不开这张表这个字段
- `term.description` 定义**一个业务概念**：「巡检计划：一次周期性巡检任务的配置模板」
  —— 独立于概念落在哪几张表

**判断方法：如果这句话必须提到某张具体的表才说得清，它就是 `description`；
不提表也说得清，才是术语定义。**

业务概念跨多个物理对象时，它的定义无处安放——那才是 `term.description` 的位置。

## 三、真正该问的问题：术语该不该是一个「节点」

上面只解决了「什么时候该有术语」，没解决「术语该长什么样」。

术语现在是 `TermWorkspaceNode`——有 id、status、confidence、候选态、要评审、占检索 8 分档。
**这套重量级机制，对「一个词有几个落点」来说太重了。** 而且它带来一个结构性缺陷：

> **搜到术语之后必须再跳一次才到表。**

三个方案被讨论过。

### 方案 A：术语保留为独立节点（现状 + 补丁）

加写入闸门、映射角色、搜索结果显示映射目标。

- 得到：概念有独立定义位置；一词多物时有个实体可评审
- 代价：**agent 永远多一跳**；空壳风险长期存在（靠闸门和评估探针压）；
  `term_mapping` 混在 `relations` 集合里那笔债留着——代码里已有特判为证
  （`WorkspaceCompletenessDto`：`continue; // 结构健康只看表间关系，术语映射不计入孤立表/degree`），
  每个遍历 `relations` 的地方都得记得这条

### 方案 B：术语降级为对象上的别名 —— **已否决**

给 `table` / `column` 加 `aliases` / `negativeAliases`，删掉 `TermWorkspaceNode` 和 `term_mapping`。

**否决理由（2026-08-28，用户提出）：语义被打散了。术语是一个聚合概念，不是分散的。**

具体打碎四样东西：

1. **概念没有家** —— 「巡检计划：一次周期性巡检任务的配置模板」无处安放
2. **没有完整性** —— 三个孤立的字符串「巡检计划」，没有任何东西绑着它们。
   改名要人肉找三处，新增第四张表没有任何东西提醒你这个概念存在
3. **反查不可靠** —— 「这个概念涉及哪些表」只能全库扫别名，是派生的不是权威的
4. **概念自己的属性无处放** —— 同义词、负向词、归属域，要么每个对象复制一份，要么丢掉

> **附带记录一个推理错误**，因为它说明判据是有效的：提出 B 时的说法是
> 「概念定义挪到主表 `description`」，而本文 2.2 节刚定下 `term.description` 与
> `table.description` 的边界。B 恰好违反了自己上一节的判据——**判据能抓住自己的错误，
> 这比结论本身更值得留下来。**

### 方案 C：术语是路由器，不是搜索结果 ← **已被取代（2026-08-30）**

> **本方案的目标已由 [术语即场景](graph-scenario-model.zh-CN.md) 覆盖且更进一步。**
> C 只解决了「命中术语时把表提上来」，场景模型在此之上加了三样它没有的：
> 入口表（子图的 `FROM` 从哪开始）、表之间的 join 路径、场景专属过滤。
> 下面的推理仍然成立，作为场景模型的由来保留。

保留术语为聚合节点（B 被否的那一点），但**不作为普通结果参与排名**——
它命中时做的是**查询扩展**：把它映射的对象提上来。

```text
搜索「巡检计划」

  ⌘ 命中术语「巡检计划」— 一次周期性巡检任务的配置模板
    同义词: 巡查计划, 任务计划 · 由该术语带出 3 张表

  ★ [TABLE] erp_prop_task_plan    业务:巡检计划 | 计划主表，title/is_scan/is_order
    [TABLE] erp_prop_task_point   业务:计划点位配置 | 计划勾选了哪些点位
    [TABLE] erp_prop_plan_point   业务:任务点位实例 | 这次任务的点位执行记录
  ─── 以下按关键词匹配 ───
    [TABLE] erp_exam_plan ...
```

同时解决四个问题：

| | |
|---|---|
| 概念是聚合的 | ✓ 术语仍是一个节点，有自己的定义、同义词、负向词 |
| 没有多余的一跳 | ✓ agent 直接拿到表，术语是上下文不是落点 |
| 空壳术语不再有害 | ✓ 不参与排名；没映射就什么也带不出来，**自然沉默** |
| `term_mapping` 有了明确职责 | ✓ **它是查询扩展的边**，不是给人看的映射清单 |

**这才是「聚合」真正兑现的地方**：聚合不是「有一个节点存着」，是
**搜一个词能一次拿到这个概念涉及的全部落点，并知道哪个是主**。当前实现只做到了前半句。

## 四、结论

1. **`businessName` / `description` / `comment` / `semanticType` / `metric` 全部保留**，
   它们各自回答别人回答不了的问题。
2. **业务描述不与术语合并。** 分工是对象不同（数据位置 vs 业务概念），不是详略。
3. **`term_mapping` 保留，职责改写**：从「展示用的映射清单」变成「查询扩展的边」。
   需要 `role: primary` 标主表（放 `attributes`，跟 `rejectionReason` 一个写法，不动模型）——
   三个落点不标主次，agent 还是要猜。
4. **术语的存在判据**（建议做成 `add-term` 的入参校验）：
   > 要么挂 ≥2 个对象，要么有同义词 / 负向词。两者都不满足 = 该写进 `businessName`，不该建术语。

   这是「先关水龙头，再擦地板」——那 5 条空壳如果有这条闸门，压根写不进去。

## 五、已经改掉的两个 bug（与方案无关，独立成立）

排查过程中发现两个真 bug，已修并有测试：

1. **实时搜索引擎完全不搜术语**（`WorkspaceSearchEngine`）。索引引擎一直在索引术语，
   但实时引擎只扫表、列、metric。后果不是排得靠后，是**索引一过期术语彻底消失**——
   真实图谱上复现过：重建索引前搜「巡检计划」，5 条术语一条都不出现。
   顺带把 `aliases` 接进匹配，否则「同义词」那一栏等于白填。
2. **搜索结果不给术语的映射目标**，agent 搜到 `[TERM] 巡检计划` 之后无处可去。
   已改成带上目标，没映射的标 `[未映射]`。
   > 方案 C 落地时这一处要**改造**（术语从「一条结果」变成「上下文行 + 把目标提上来」），
   > 第 1 条保留（扩展的前提是术语能被匹配上）。

## 六、未决

方案 C 拍板后要定的实现细节：

- 查询扩展带出的对象与关键词命中的对象**怎么合并去重**，扩展项的加权多少
- 术语上下文行在 `--json` 输出里怎么表达（agent 要能区分「这是术语带出来的」）
- `role: primary` 的写入口（`add-term --map` 怎么标主）
- 写入闸门的报错文案：要直接给出「你应该改用 `schema edit --business-name`」
- 现有 5 条术语的处置：按第四节判据，「顺序巡检」（只对应 `is_order`、无同义词）应删除，
  其余 4 条补映射 + 定义；「扫码」需要加 `negativeAliases: ["扫码打卡"]` 挡考勤域
