# 图谱模型与 ER 模型：定位、边界与加强方向

> 类型：**设计依据**，不是进度清单。这里定的是"我们的图谱和 ER 模型是什么关系、
> 哪些地方必须遵守 ER 的既有共识、哪些地方是有意的扩展"。
>
> 相关：[元数据模型设计](database-graph-metadata-model-design.zh-CN.md)（模型定义本身，权威）、
> [产品演化方向](product-evolution-direction-2026-08.zh-CN.md)（这份结论的下游动作）。
>
> 立此文档的原因：图谱里已经有了 `join_observed`、`term_mapping`、`LineageRecord`、
> `SemanticType`、`confidence/status` 这些 ER 里不存在的东西。如果不写清楚"哪些是 ER、
> 哪些不是 ER、为什么可以不是"，下一个人要么会把它们当成 ER 的一部分去做语义推理（错），
> 要么会以为我们在另起炉灶抛弃 ER（也错）。

---

## 一、结论

**ER 模型和我们的图谱不是同类工件，因此谈不上"违背"。**

- **ER 模型是设计期工件**，回答"这个库应该怎么建"。理论前提是：设计者掌握全部语义、
  schema 干净、已规范化、约束完整。
- **我们的图谱是使用期工件**，回答"这个已经跑了五年的库里，我要的东西在哪、怎么查才对"。
  现实前提是：499 张表、列名叫 `f_yhsjh`、注释为空、团队根本没建外键、
  文档写着"废弃勿用"但表里还在写数据。

ER 没有解决后一个问题，不是因为 ER 不好，是因为那从来不是它的目标。

**但有一个真实风险：我们在扩展语义层的同时，把 ER 里那些"硬约束"丢掉了，
而丢掉的恰恰是直接影响生成 SQL 正确性的部分。** 本文第四节列出该捡回来的三样。

---

## 二、我们是 ER 的超集：三个维度

ER 模型里完全没有对应物的东西：

| 维度 | ER 模型 | 我们 | 为什么必须有 |
|---|---|---|---|
| **业务语义** | 无。attribute 只有 domain（取值范围），没有"这个字段在业务上是什么" | `businessName`、`SemanticType`（21 种，分敏感信息/业务含义/系统字段三组）、`ColumnValueHints`（含 `0=待付款` 这种口径） | 列名是 `f_yhsjh` 时，domain 是 `varchar(11)` 毫无帮助；"买家手机号 / phone / 敏感" 才有用 |
| **可信度与来源** | 无。一条关系要么存在要么不存在 | `confidence`、`RelationEvidence`、`status`（candidate → verified）、`actor`（extractor/agent/human） | 关系是 Agent 从代码里推断出来的，必须能表达"还没人确认过"，否则人工知识和机器猜测混为一谈 |
| **检索** | 无。设计者面对的是自己设计的 20 张表 | BM25 + CJK bigram 分词 + 人工 `boost` | 面对 499 张表和一个不认识它们的 LLM，"找得到"是前置问题 |

## 三、关键区分：我们没有污染 ER 的关系语义

这是"不违背 ER"最实质的一条，值得单独说清楚。

我们有三种关系类型，**它们不是"ER relationship 的三个子类"，而是三个不同性质的层**：

| 类型 | 是不是 ER 的 relationship | 性质 |
|---|---|---|
| `foreign_key` | **是**。严格对应 ER 的 relationship set | **声明的**。由数据库导入维护，人和 Agent 不能创建或编辑 |
| `join_observed` | **否**。ER 里没有这个概念 | **经验的**。从实际写过的 SQL 里观察到"这两张表被这样连过" |
| `term_mapping` | **否**。属于 business glossary 层，不是数据模型层 | **词汇的**。业务术语 → 数据对象的指向 |

ER 的 relationship 表达的是**设计意图**：设计者认为这两个实体之间存在这种联系。
`join_observed` 表达的是**经验事实**：有人这样连过、跑通了。两者可以并存且不矛盾——
一张没建外键的库里可能有 200 个 `join_observed` 和 0 个 `foreign_key`，这不代表
ER 意义上没有关系，只代表关系没被声明。

**因此我们的原则是：**

> **ER 的部分保持 ER 的语义纯度，扩展的部分明确标记为非 ER，两者不混用于同一推理。**

具体约束（可执行，不是口号）：

1. `foreign_key` 边的基数/可选性语义严格遵循 ER 记法共识，且**只能由导入写入**——
   这条已经在代码里强制（人和 Agent 不能创建 `foreign_key`）
2. `join_observed` / `term_mapping` **不参与** ER 语义推理（比如不能拿它推导实体完整性）
3. 字段血缘（`LineageRecord`）**不是关系类型**，是与 terms 平级的第三个集合——
   它是 n 元推导、要带产生上下文、规模比关系大两个数量级。
   决策与理由见 [dev-checklist P3 字段级血缘](dev-checklist-2026-08.zh-CN.md) 一节。
   **别再把 `lineage_to` 加回 `RelationType`。**

## 四、我们是 ER 的子集：该捡回来的三样

ER 有成熟理论和行业共识、我们缺、且**直接影响 Agent 生成的 SQL 对不对**的三项。
这就是"加强 ER 而不是违背它"的具体内容。

### 4.1 参与约束 / optionality（最高价值）

**ER 的共识**：Crow's foot（IE 记法）和 Barker 记法里，关系线的每一端都有**两个**符号——
一个表示基数（one / many），一个表示可选性（`O` 圆圈 = 可选，`|` 竖线 = 强制）。
"每个订单必须有一个客户" 与 "订单可以没有客户" 是两种不同的关系，画法不同。

**我们的现状**：`RelationCardinality` 只有 `one_to_one` / `one_to_many` / `many_to_one` /
`many_to_many` / `unknown`——**只有基数，没有可选性**。

**为什么这条最要紧**：可选性直接决定 **`INNER JOIN` 还是 `LEFT JOIN`**。
这是 Text-to-SQL 最高频的错误来源之一，而且**错了是静默的**——
用 `INNER JOIN` 连一个可选关系，结果少了行，没有报错，没人会发现。

**半自动推导路径**：外键列 `nullable = true` → 该端大概率可选。
`ColumnWorkspaceNode` 已经存了 `nullable`，导入时即可给出初值，
剩下的走候选评审由人确认。

### 4.2 函数依赖 / 权威来源

**ER 的共识**：规范化理论（1NF → 2NF → 3NF → BCNF）建立在函数依赖之上，
其目的就是消除冗余副本、确立单一事实来源。

**我们的现状**：完全没有这一层。

**后果**：宽表里的 `customer_name` 是下单那一刻的冗余快照，权威源在 `customer` 表。
Agent 检索到哪个就用哪个，可能拿到的是历史快照而不是当前值——
同样是**静默错误**，查出来有数，但不是用户想问的那个数。

**注意边界**：我们**不做规范化建议**（"你这张表不满足 3NF，建议拆分"）——
那是设计期的事，不是我们的定位。我们只需要标注"这个列是那个列的冗余副本"，
让 Agent 知道权威源在哪。

### 4.3 弱实体 / 标识关系

**ER 的共识**：弱实体（weak entity）不能独立存在，必须依赖强实体标识；
记法上用双线矩形 + 双线菱形表示标识关系。典型就是 `order_item` 依赖 `order`。

**我们的现状**：没有这个概念。明细表和主表看起来是平等的两张表。

**后果**：Agent 可能直接查明细表而不带主表的过滤条件，生成全表扫描；
或者不理解"查明细必须先定位主单"这个业务约束。

**半自动推导路径**：复合主键里包含指向另一张表的外键 → 强标识关系信号。
主键和索引信息我们都已经存了。

## 五、明确不做

为了不让"向 ER 靠拢"滑成"重做一个 ER 工具"：

- **不做 ER 图绘制/建模工具**。设计新库请用 PowerDesigner / ERwin / dbdiagram，
  我们不进这个场。我们的画布是为了**理解现存的库**，不是为了设计新库。
- **不做规范化建议**。见 4.2 的边界说明。
- **不做 DDL 生成 / 正向工程**。ER 工具的核心能力之一，明确不是我们的方向。
- **不把 ER 缺失的东西补成"完整 ER 模型"**。只补第四节那三样——
  判据是"是否影响生成的 SQL 正确性"，不是"ER 里有没有"。

---

## 六、一句话总结

> 我们不是 ER 的替代品，也不是 ER 的实现。
> 我们是**在 ER 描述的结构之上，叠加语义层、可信度层与检索层，服务于"使用"而非"设计"**。
> ER 已有共识的部分（基数、可选性、标识关系、函数依赖）严格遵守并逐步补齐；
> ER 没有覆盖的部分（业务语义、来源可信度、经验关系、术语映射、字段血缘）
> 明确标记为扩展，不与 ER 语义混用。
