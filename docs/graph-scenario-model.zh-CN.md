# 术语即场景：从「一个词对应哪些表」到「这件事要用哪些表」

> 状态：**方案已定，未实现**。取代 [图谱语义机制](graph-semantic-mechanisms.zh-CN.md)
> 第三节的方案 C（术语作路由器）——该方案的目标被本文覆盖且更进一步。

## 范围

术语不新增对象类型，升级为**场景载体**：命中一个术语时，除了同义词，还能给出
「完成这件事需要哪些表、怎么连、要带哪些过滤」。

## 层与三问

- **层**：语义层（术语本身）∩ 结构层（子图由已有关系推导）
- **产出**：agent 读**前端面客代码**（表单 label、列头、菜单、筛选项）识别场景，
  再到后端确认落点，一次 `add-term` 写齐 `--aliases` / `--map` / `--primary-target` / `--filter`
- **消费**：agent 搜索命中术语时直接拿到子图与过滤；`describe` 一张表时反向得知它属于哪些场景
- **它挡的错**：术语只给点不给边，agent 拿到 4 个孤立的词后自己拼 join——
  拼错的后果是跨租户笛卡尔积、漏软删除、漏项目隔离，**SQL 照跑、有结果、数是错的**

## 总规则

**一条术语能不能给出子图，由 `primaryTarget` 指向什么决定，不由声明决定。**

| `primaryTarget` | 行为 |
|---|---|
| 指向一张**表** | 能给出场景子图 |
| 指向一个**列**，或未填 | 退化为同义词路由（今天的行为） |

不引入 `kind: concept \| scenario` 之类的声明字段：声明可以和事实不符，
一条标着 `scenario` 却没有入口表的术语是不报错的坏数据。

## 数据模型

`TermWorkspaceNode` 新增两个字段，不新增对象类型：

| 字段 | 类型 | 说明 |
|---|---|---|
| `primaryTarget` | ref，可空 | 入口表或列，格式同 `--map`。子图的 `FROM` 从这里开始 |
| `filters` | 字符串列表，可空 | **场景专属**过滤。元素是完整条件（`state IN (0,1,6)`）或带占位符的必填参数（`subject_id = :subjectId`） |

### `filters` 装什么、不装什么

判据：**换一个场景这条还成不成立**。

| 例子 | 归属 |
|---|---|
| `del_flag = 0` | **不进 `filters`**，是全库约定，走 policy 约定规则 |
| `state IN (0,1,6)`（未完结的报事） | 进 `filters`。同一张表在回访场景是 `state IN (6,7)` |
| `is_nock = 1 AND state = 0`（可抢单） | 进 `filters` |
| `subject_id = :subjectId`（所属项目） | 进 `filters`，**占位符形式**——值运行时给，但位置必须有 |

占位符与常量条件同列表，agent 一次取全。看到 `:name` 即知必须向用户取值，
不得省略——漏掉项目隔离列会查到别的项目的数据。

### policy 新增一类规则：约定

现有规则全是**断言**（「这必须成立」），产出 violation 给人看。新增**约定**类型：

- `when` 匹配对象（**列名 + 值域**，不是无条件全库套用）
- 产出不是 violation，是**注入查询上下文的提示**，消费者是 agent
- 例外复用已有的 `policy/waivers/`

匹配必须带值域条件。反例是真的：`erp_prop_report.del_flag` 注释写
`0代表存在 2代表删除`，而实测「库里存在未声明的值 1；声明了但库里从未出现 2」。
一条无条件注入 `del_flag = 0` 的规则在这张表上恰好蒙对，
但只要有一张表用 `del_flag = 1` 表示存在，同一条规则就会静默筛掉全部数据。

## 行为规格

### 子图推导

| 步骤 | 规则 |
|---|---|
| 入口 | `primaryTarget` 指向的表 |
| 表集合 | `term_mapping` 映射的表 ∪ 入口表 |
| 边 | **仅**表集合内部已有的 `relation`，不展开额外跳 |
| 不连通时 | 用 `schema path` 求最短路径，补路径上的桥接表，标注为「桥接」 |
| 输出格式 | 从入口表出发的树，每跳复用 `schema path` 现有格式：完整 `ON` 条件 + `INNER/LEFT（推断）` 标记 |

**不展开 1 跳。** 531 表的库上一跳能拉出几十张表，且每多一张就是 agent 多一个连错的选择。
真需要字典表时 `describe` 那张表本来就带关系。

**不输出可执行的 `FROM ... JOIN ...` 文本**：那会与 `MetricRecord.joinPath` 撞车。

### `search`

命中术语时术语**不占结果位**，改为：

- 顶部一行上下文：术语定义、同义词、由它带出几张表
- 子图的表**提到关键词匹配结果之前**，入口表标记为主
- `primaryTarget` 不指向表时，退化为今天的行为（同义词参与匹配，不带子图）

空壳术语因此自然沉默：没有映射就什么也带不出来，不再劫持 Top1。

### `describe`

反向索引：列出这张表**属于哪些场景**，以及**命中它的约定规则**（如 `del_flag = 0`）。

约定规则在 `describe` 和 `search` 两处都注入——agent 完全可能不经过场景直接 describe 一张表。

### `add-term` 写入闸门

| 情况 | 处理 |
|---|---|
| 同义词、描述、映射**三样全空** | **硬拒**，退出码 1 |
| `--primary-target` 指向图谱中不存在的对象 | **硬拒**，退出码 1（与 `add-lineage` 的 `Column not found` 一致） |
| 映射的表之间不连通 | **仅警告**——很可能是关系还没录进图谱，不是术语写错了 |

这是 breaking change，所以硬拒条件只取无可争议的两条。

### 审批

场景写入是图谱写入，走既有管线（条目 / 批次 / `graphApproval`），无特殊路径。

`filters` 在评审卡片上标为高风险（写错是静默少数据），
**但这只影响显示，不影响谁来批**——按内容类型决定裁决路径就是 #154 那个小灶。

## CLI

```bash
sql-cli <alias> schema add-term 报事 \
  --display-name "报事" --aliases "工单,报修,报事单" \
  --description "住户提交的一次维修请求" \
  --map <schema>.erp_prop_report,<schema>.erp_prop_report_assign \
  --primary-target <schema>.erp_prop_report \
  --filter "state IN (0,1,6)" --filter "subject_id = :subjectId"
```

**不新增 `schema scenario` 子命令**：`search` 已经能带出子图，再开一个入口就是两个入口。

## UI

**术语不是一个平行的清单，是图谱的一个筛选维度。**
（这句**只管术语与表视图的关系**。术语之间若建立关系，术语网络本身是另一张图，
不在这句的射程内——见 [术语网络](graph-term-network.zh-CN.md)。）

现状要改的地方：图谱页左侧栏四个 tab 平行（表目录 / 术语 / 指标 / 血缘），
术语 tab 是只读列表，映射目标是几个**点不动的字符串**——看完还得自己回表目录一张张找。

| | 改后 |
|---|---|
| 术语 tab | 保留作目录（有哪些术语）。**点一条 = 应用筛选**，切到表目录 |
| 表目录 | 只剩这条术语的表；入口表标「主」，为连通补进来的标「桥接」 |
| 关系视图 | 只剩这些表之间的边 |
| 顶部 | 显示 `filters` 与命中的约定规则 |
| 取消筛选 | 回到全库 |

筛选状态进 URL（`?term=报事`），与现有 `?alias=` 一致——可分享、刷新不丢。

**零新页面、零新组件**：表目录本来就有按 schema 的筛选，这是多一个维度。
与 CLI 侧同构——`search` 把术语的表提上来，UI 里就是把表目录筛到它的表。

| 文件 | 改什么 |

## 评测

**判据只有一条**：给定一个业务问题，agent 生成的 SQL 是否带全了必要的 join 条件与默认过滤。

Top1 / MRR 测的是检索，而本次改造的收益全在检索**之后**，那两个指标测不到。
扩 `docs/task-eval-erp-inspection.yaml`。

## 现有 9 条术语的处置

**等能力实现后，由 agent 用一个批次提交，人整批审**（intent：按场景模型重整现有术语）。
现在补 `primaryTarget` 没有意义——字段还不存在，写了没人消费。

| 术语 | 处置 |
|---|---|
| `顺序巡检` | 删除。同义词、描述、映射三样全空，新闸门下本就写不进来 |
| `扫码`、`检查项`、`巡查点位` | 补描述。`primaryTarget` 指向列或留空，保持同义词路由 |
| `报事`、`工单`、`抢单`、`回访满意度`、`巡检计划` | 补 `primaryTarget` 与 `filters` |

## 明确不做

- **新增 `scenario` 对象类型**（术语即载体，先验证价值再谈加对象）
- **`kind: concept \| scenario` 声明字段**（可与事实不符的字段比没有更糟）
- **可执行 SQL 骨架**（metric 的地盘）
- **表级 `defaultFilter` 字段**（531 份重复，改用一条 policy 约定规则）
- **`schema scenario` 子命令**（search 已是入口）
- **子图展开 1 跳及以上**
- **关键字段子集**（一张表 50 个字段场景只用 8 个）——观察档，等子图跑起来看 agent 缺不缺
