> 类型：**顶层结构梳理**，不是执行清单。条目落到
> [dev-checklist-2026-09](dev-checklist-2026-09.zh-CN.md)。
>
> 起因：2026-08-28。八个概念（语义类型、值域、术语、指标、血缘、关系、表/字段业务描述、

## 一、唯一目的，和由它推出的判据

**目的：给 agent 足够准确的上下文，让它能做四件事——设计数据库、梳理业务、查询数据、
给用户准确的判断结论。**

由它推出的判据。之前定过半条：

> 一个语义机制存在的理由 = 它能回答别的机制回答不了的问题。

那半条只挡住了重复，挡不住「堆功能」——一个不重复但也没人用的概念照样是堆的。
补齐成**三问**，每个概念都必须答得出：

| | 问题 | 答不出会怎样 |
|---|---|---|
| **产出** | 谁写、什么时候写 | 永远是空的 |
| **消费** | agent 在**哪一步**读它、读了**做什么决定** | **它是死的**，写了没人用 |
| **失败** | 没有它，agent 会犯**什么具体的错** | **它不可评测**，好坏说不清 |

**第三问同时就是它的评测判据。** 说不出「没有它会犯什么错」的概念，既不能证明有用，
也不能证明没用——那正是「效果评测没有体现」的根因，不是评测没做，是**概念本身没定义可失败的东西**。

## 二、三层模型：agent 做一件事需要三层信息

```
第三层  口径层    metric                                    「这个业务问题怎么算」
                      ↑ 消费下面两层，不与它们并列
第二层  语义层    术语 · 业务描述 · 值域 · 语义类型 · 血缘     「这个字段是什么意思」
                      ↑
第一层  结构层    表 · 字段 · 关系                            「库里有什么、怎么连」
```

**`metric` 不是第八个并列概念，它是站在另外七个之上的一层。** 一条指标要落地，
需要结构层给表和 JOIN、语义层给字段含义和值域。把它跟术语、血缘并排列会看不出这件事。

### 数据质量不是一层，是每一层各自的正确性

用户问的「数据质量图谱 和 数据库存储的数据质量」——**它们不是两个功能，是同一个「质量」
作用在不同层上**：

| 层 | 质量问的是 | 现有工具 | 状态 |
|---|---|---|---|
| 结构层 | 库**设计**得对不对（主键、索引、命名、类型） | `schema policy` | 有，14 条规则 |
| 语义层 | **图谱**够不够、准不准（覆盖率、空壳术语、值域缺失） | `schema eval` | **设计完，未实现** |
| 数据层 | 库里的**值**对不对（脏值、空值率、孤儿外键） | — | **空白** |

**已核实的两件事，都影响这张表的读法：**

1. **`schema policy` 完全不连库**——14 条规则全部只读图谱。所以它评的不是「库」，
   是「**图谱记录的那个库**」。图谱一旦过期，policy 检查的是一张过期的图。
2. 数据层没有任何东西。**而 agent 犯的最贵的错恰恰在这一层**——值域理解反了、
   拿了一个全 NULL 的字段做判断，SQL 照跑、照出数、不报错。

> 值域三源交叉（`graph-eval.md` §4）正好踩在语义层和数据层的边界上：它读库里的实际分布，
> 既补图谱（元数据），又发现脏数据（数据质量）。**这是唯一一个同时服务两层的探针，
> 所以它排第一。**

## 三、八个概念逐个过三问

### 1. 表/字段业务描述（`businessName` / `description` / `comment`）

| | |
|---|---|
| 产出 | `comment` 由导入写（DB 注释镜像，唯一非人写的事实）；另两个由人/agent 写 |
| 消费 | **检索定位**（搜业务词命中）+ **选表判别**（三张名字像的表选哪张） |
| 失败 | 找不到表；**选错表**（`erp_prop_task_point` 配置态 vs `erp_prop_plan_point` 执行态，选错照样出数） |
| 评测 | `search-eval` Top1/Top5/MRR + 易混组区分 |

**判定：核心，不可替代。** 三者分工已定（见语义机制文档 2.2）：`comment` 是库的镜像，
`businessName` 是 1:1 的名字，`description` 是「这个数据位置怎么回事」。

### 2. 语义类型 `semanticType`

| | |
|---|---|
| 产出 | 人/agent，固定枚举词表 |
| 消费 | **执行期**——该不该 SM4 脱敏、怎么格式化、值域怎么推 |
| 失败 | 手机号没脱敏就查出来了；金额当整数算 |
| 评测 | **可自动**：抽样比对「标了 `phone` 的列里的值是不是真的手机号」 |

**判定：核心，但边界现在是糊的。**

> **已核实的越界**：`WorkspaceSearchEngine` 把 `semanticType` 的枚举名和中文标签
> 都加进了检索匹配（`WEIGHT_SEMANTIC_TYPE`）。它本该是**执行期信号**，不是检索信号。
> 混进去的后果是搜「手机号」会命中一批只是标了 `phone` 而业务上不相关的字段。
>
> **要不要拆是个待定项**——好处是边界清晰、检索更准；代价是失掉一条召回路径
> （有些字段除了 `semanticType` 什么描述都没有）。**先记，别顺手改。**

### 3. 值域 `valueHints`（`enumValues` / `format` / `sampleValues`）

| | |
|---|---|
| 产出 | **三源交叉**：库里 `GROUP BY` 分布 × 字段注释 × 代码枚举 |
| 消费 | **写 WHERE 条件时**——`is_scan=1` 到底是「必须扫码」还是「免扫码」 |
| 失败 | **安静地出错数**。这是全部失败模式里最贵的一类 |
| 评测 | 库里出现声明外的值 = 硬错误（全自动） |

**判定：核心，而且是当前最欠缺的。** 它是唯一一个「评估顺便把图谱补好了」的概念。

### 4. 关系 `relation`（`foreign_key` / `join_observed`）

| | |
|---|---|
| 产出 | 导入（FK 是库里声明的）、agent 读代码、执行历史挖掘 |
| 消费 | **选 JOIN 路径**，含 INNER/LEFT 判断 |
| 失败 | JOIN 错、方向反、扇形陷阱——**同样安静地出错数** |
| 评测 | path-eval（给两张表，看产出的路径对不对）——**现在没有** |

**判定：核心。** 但注意 `term_mapping` 混在同一个集合里是笔已知的债
（它是「词指向什么」，不是「数据怎么连」），见语义机制文档。

### 5. 血缘 `lineage`

| | |
|---|---|
| 产出 | agent 读代码（Mapper / ETL / 视图定义） |
| 消费 | **判断这个值是不是原始的**——`task_point.qr_code` 是 `public.qr_code` 的快照，可能过期 |
| 失败 | 拿快照当权威值查，得到过期数据 |
| 评测 | 无 |

**判定：合格，但价值密度最低，暂停投入。** 诚实说清楚：

> **2026-09-08 重判。** 这条判定写在「查询数据」目的下。09-03 目的收窄成修 bug / 重构之后，
> 「改这个字段哪些下游值会跟着错、改动在哪个方法里」只有血缘答得出（`through` 指的就是那个方法），
> 它从「价值密度最低」变成重构目的下的主消费方之一。模型补了四类（identity / transformation /
> aggregation / rule，按 OpenLineage 的 DIRECT / INDIRECT 收编），消费落在 `describe --column` 的下游列表。
> 拍板与清单见 [dev-checklist-2026-09](dev-checklist-2026-09.zh-CN.md) L1 节。下面的原文保留。

- 真实图谱里只有 **8 条**，而关系有 89 条、字段有 10114 个
- **消费路径直到 2026-08-28 才接通**（此前搜索结果里完全不提血缘，agent 根本看不见它）
- 它的失败模式（拿快照当原始值）比值域和关系的失败模式**罕见得多**

**不是堆功能**（三问都答得出），但**在值域和关系补齐之前不该继续投入**。
已建的东西（弹窗、左栏视图、搜索标记）够用了，不要再加。

### 6. 术语 `term`

| | |
|---|---|
| 产出 | agent / 人 |
| 消费 | **检索的查询扩展**——一个业务词带出它涉及的全部落点 |
| 失败 | 搜业务词找不到对的表 |
| 评测 | `search-eval`，尤其是「一词多物」那类 case |

**判定：核心，但当前实现错位。** 它现在是「一条参与排名的结果」，应该是「一个路由器」
（方案 C，见语义机制文档）。存在判据也已定：**要么挂 ≥2 个对象，要么有同义词/负向词**，
两者都不满足时它与 `businessName` 完全重叠。

### 7. 指标 `metric`

| | |
|---|---|
| 产出 | 人定义口径（不是 agent——口径是业务决定，不是能从库里读出来的事实） |
| 消费 | **`expand-metric` 展开成 SQL** |
| 失败 | 口径不一致，两个人算出两个数还都说自己对 |
| 评测 | 展开出的 SQL 能不能跑、结果能不能手算复核 |

**判定：核心，但它在第三层**，消费另外七个而不与它们并列。

> **已知的断裂**：`TableWorkspaceNode.grain` 有写入口、有 policy 规则催着填，
> **但没有任何消费方**（F5 扇形陷阱检查没做）。这是本文判据里
> 「答不出消费 = 它是死的」的一个现成例子，清单 F5 条目已记。

### 8. 数据质量

见第二节——**它不是一个概念，是三层各自的正确性**，对应三套工具，其中一套（数据层）不存在。

## 四、使用场景矩阵：四个任务分别消费什么

这是「使用方式不清」的答案。**产**=这个任务产出它，**消**=这个任务消费它。

| 概念 | 设计数据库 | 梳理业务 | 查询数据 | 给判断结论 |
|---|---|---|---|---|
| 业务描述 | **产** | **产** · 消 | **消**（定位 + 判别） | 消 |
| 关系 | **产**（FK 设计） | 消 | **消**（选 JOIN） | — |
| 语义类型 | **产**（该不该脱敏） | — | **消**（脱敏 / 格式） | 消（合规） |
| 值域 | **产**（枚举设计） | 消 | **消**（写 WHERE） | **消**（口径） |
| 术语 | — | **产** · 消 | **消**（检索扩展） | — |
| 血缘 | — | 消（影响面分析） | 消（是不是原始值） | 消（这个数从哪来） |
| 指标 | — | **产** | 消（展开 SQL） | **主要消费方** |

**三条读法：**

1. **「设计数据库」是纯产出侧。** 设计的那一刻是**唯一免费产出语义的时机**——
   你按聚合根切出订单行的同一秒就知道它的粒度和角色，三年后再问就是考古
   （清单 F2 的论证）。当前缺口是设计阶段只收了一半产物。
2. **「查询数据」是最重的消费方**，七个概念里消费六个。所以检索质量 = 产品质量。
3. **「给判断结论」几乎全靠 metric + 值域。** 结论要能被复核，靠的是口径明确和值域正确，
   不是靠更多的描述文字。

## 五、边界不清的三处，具体怎么划

| # | 现状 | 划法 |
|---|---|---|
| 1 | `semanticType` 混进了检索匹配 | 它是**执行期**信号，不是检索信号。**待定**：拆掉更干净，但会丢一条召回路径 |
| 2 | `term_mapping` 混在 `relations` 里 | 「词指向什么」≠「数据怎么连」。**记债不还**（拆要动模型和落盘格式） |
| 3 | `policy`（评库设计）与 `eval`（评图谱）容易被当成一件事 | **两个命令不合并**。一个评元数据、一个评库设计，混一份报告读的人分不清在说谁 |

## 六、效果评测方案：用 agent 和 skill 本身来测

评测的对象不是「图谱有多全」，是**agent 拿着它能不能把活干对**。所以评测必须让 agent 真的干一遍。

### 6.1 跑法

```
一个任务（自然语言）
   ↓
起一个 agent，只给它 sql-cli skill，不给库的直连、不给答案
   ↓
它产出：用哪几张表 · 怎么 JOIN · 关键字段取什么值 · 最终 SQL
   ↓
对照 expect 自动判分（表集合 / JOIN / pitfalls）
```

评测集格式已有初稿：`docs/task-eval-erp-inspection.yaml`（10 个任务）。
关键字段是 **`pitfalls`**——它把「安静地出错数」变成可判定的。
只写 `tables` 和 `joins` 测不出「选错了名字相近的那张表」，因为那种 SQL 照样能跑。

### 6.2 核心设计：把「图谱不够」和「agent 不行」分开

**这是整个方案里最值钱的一条。** 不分开的话，一次失败什么也说明不了——
可能是图谱缺信息，也可能是 agent 笨，两者的修法完全相反。

同一个任务跑两组：

| 组 | 给什么 | 失败说明什么 |
|---|---|---|
| **对照组** | 只给图谱 | — |
| **作弊组** | 图谱 + 正确的表集合（只隐藏 JOIN 和值域） | — |

| 对照组 | 作弊组 | 结论 | 该修哪 |
|---|---|---|---|
| ✗ | ✗ | **agent 能力问题**（给了表还做不对） | 改 skill 的指引，不是补图谱 |
| ✗ | ✓ | **图谱信息不足**——定位环节缺东西 | 补描述 / 术语 / 检索 |
| ✓ | ✓ | 通过 | — |

**没有这个对照，任务通过率是一个无法归因的数字，看了也不知道该做什么。**

### 6.3 skill 也是被测对象

`sql-cli` skill 的 `references/*.md` 是 agent 的操作指引。上表第一行（两组都失败）
指向的就是 skill 而不是图谱。所以评测同时在测两样东西，报告要分开写：

- **图谱侧失败** → 进 `schema eval` 的工作队列（有可执行命令）
- **skill 侧失败** → 改 `references/` 里对应那一节，并记下改的是哪句话

### 6.4 三个指标，各自答一个问题

| 指标 | 答的问题 | 来源 |
|---|---|---|
| 硬错误数 | 图谱里有没有**确定是错**的东西 | 自动探针，必须为 0 |
| 检索命中率 | 业务词**找不找得到**对的表 | `search-eval` |
| **任务通过率（对照组）** | agent **能不能把活干对** | 任务评测集 |

前两个是代理指标，第三个才是目标。**代理指标涨而任务通过率不涨，说明补错了地方**——
这个信号本身就有价值。

### 6.5 为什么不能只靠人工看

已实测过一次反例：5 条空壳术语让 Top1 从 55.6% 掉到 11.1%。
**人工翻图谱看不出这件事**——那 5 条术语单独看每一条都「没问题」，
只有在检索排序里才显出害处。评测必须是端到端的、可复现的、有数的。

## 七、诚实结论：哪些是堆的

拿第一节的三问过一遍：

| 概念 | 产出 | 消费 | 失败 | 判定 |
|---|---|---|---|---|
| 业务描述 | ✓ | ✓ | ✓ | 核心 |
| 值域 | ✓ | ✓ | ✓ | **核心，最欠缺** |
| 关系 | ✓ | ✓ | ✓ | 核心 |
| 术语 | ✓ | ⚠ 错位 | ✓ | 核心，实现要改 |
| 语义类型 | ✓ | ✓ | ✓ | 核心，边界要划 |
| 指标 | ✓ | ⚠ grain 无消费方 | ✓ | 核心，F5 是缺口 |
| 血缘 | ✓ | ⚠ 刚接通 | ✓ | 合格，**暂停投入** |
| 数据质量（数据层） | — | — | — | **不存在，是真空白** |

**没有一个概念是纯粹堆出来的**——八个都答得出三问。「堆功能」的感觉来自另外三件事：

1. **消费路径长期没接通。** 血缘写了但搜索不提它、`grain` 填了但没人读、术语挂了映射但
   搜索不显示。**写入口做完就算完，消费侧没人做**——这是产生「堆」的真正机制。
2. **失败模式没被度量。** 每个概念都能说出「没有它会犯什么错」，但**从来没有人测过那个错
   到底发不发生**。所以功能一直在加，好坏一直说不清。
3. **质量分成三层这件事没有被说出来过。** 于是 `policy`、`eval`、数据检查看起来像三个
   互相重叠的东西，实际上是三层各管一层、其中一层根本不存在。

**结论：不要再加第九个概念。** 该做的是把三处消费路径接通（术语方案 C、F5 扇形陷阱、
值域三源交叉），然后用第六节的方案把失败模式测出来。

> **2026-09-03 补记。** 三处消费路径已接通两处（值域三源交叉 E1、术语→场景 S1~S4），
> 第三处 F5 改道进 D1。**但复盘时数出来的东西比「消费路径」更靠前**：
> 499 表 / 10426 列里只有 41 处 `description`、22 处 `enumValues`、0 条 metric。
> 消费路径全接通了，**读到的还是空的**。
>
> 这不是产能失败——`code-scan.md` 明确禁止全仓扫描，图谱是**按需生长**的，
> 覆盖率是「在这个库上真正干过多少活」的函数。但它带出一个本文没覆盖的问题：
> **按需生长下，「够不够」没有判据**，而 agent 无法区分「没描述因为表简单」和
> 「没描述因为没人干过这块」。那正是 D1 第 1 项要补的东西。
