# 一、驱动管理

## 现状

CLI 已完整：`driver list / show / add / update / remove / default`。
配置在 `config/settings.yaml`：

```yaml
driverDefaults:          # 按 dbType 指定默认驱动
  mysql: mysql8
drivers:
  mysql8:
    dbType: mysql
    driverClass: com.mysql.cj.jdbc.Driver
    jars: [./drivers/mysql/mysql-connector-j-8.3.0.jar]
```

UI 完全没有，设置页只写了一行「仅 CLI 可用」。

## 为什么值得做

驱动配置错误是新装用户第一个撞上的墙，而且报错信息离根因很远：jar 路径写错了，
用户看到的是「连接失败」；驱动类名拼错了，看到的还是「连接失败」。
把这些前置校验做进 UI，能省掉大量「为什么连不上」的排查。

## 功能清单

### D1 驱动列表（必做）

| 列 | 说明 |
|---|---|
| 名称 | 驱动引用名（别名里 `driverRef` 用的就是它） |
| 类型 | dbType，标出是否为该类型的默认驱动 |
| 驱动类 | driverClass |
| jar 状态 | **绿=文件存在且可加载 / 黄=文件存在但类加载失败 / 红=文件不存在**（配色沿用 CLAUDE.md 状态色规则） |
| 引用 | 有几个别名在用它 |

jar 状态是这一页的核心价值：它把「连接失败」提前暴露成「驱动 jar 找不到」。
校验方式是本地文件存在性 + 用隔离 ClassLoader 试 `Class.forName(driverClass)`，
不连数据库，毫秒级，可在列表加载时全部跑一遍。

### D2 新建 / 编辑驱动（必做）

- 选 dbType 后自动填入常见驱动类名（mysql/postgresql/oracle/clickhouse 四个内置默认值），可改
- jar 路径支持多个（Oracle 有时要 ojdbc + orai18n 两个）
- 保存前跑一次 D1 的校验，失败给出具体原因而不是让用户保存完再去试连接
- 名称唯一性校验；编辑时名称不可改（别名靠它引用）

### D3 删除保护（必做）

被别名引用的驱动不允许删除，提示「有 N 个别名正在使用：xxx, yyy」。
**这个校验现在 CLI 里也没有**，要一并补上，否则删掉驱动后别名静默失效。

### D4 设为默认（必做）

每个 dbType 一个默认驱动，新建别名时不填 `driverRef` 就用它。

### D5 jar 获取方式（后置，看反馈）

现在只支持填本地路径。可选的增强：
- 文件上传：浏览器上传 jar 到 `./drivers/{dbType}/`
- Maven 坐标下载：填 `mysql:mysql-connector-j:8.3.0` 自动拉取

**建议先都不做。** 上传要处理大文件和路径穿越，下载要处理网络、代理和校验和——
而用户装驱动是一次性动作，手动放文件并不痛苦。等真有人抱怨再说。

## 交付顺序

D1 + D2 + D3 + D4 是一个批次，约 2~3 天（含后端 4 个端点 + 一个校验服务）。
做完设置页那句「仅 CLI 可用」就只剩 `secret status / delete` 了。

# 二、SQL 工作台

## 依赖

**必须等批次 4（SqlTaskModule + 结构化查询结果）**。
在单一入口建成之前不要开工——否则工作台会自己长出第二条执行路径，
将来收编的成本比现在等着高得多。

现成可复用的：`ResultTable` 组件（批次 4b 做的，列头带类型、NULL/长文本处理、截断提示）、
`SqlRerunController` 的只读语句白名单、`schema search` 索引（做补全用）。

## 功能清单

### W1 编辑与执行（必做）

- 纯 `textarea` + 等宽字体，**不引 Monaco**（开发清单「明确不做」已定）
- Ctrl/Cmd + Enter 执行，Esc 取消
- 顶部上下文条：当前 alias + schema 选择器（多 schema 支持落地后，这里决定不写 schema 前缀时用哪个）
- 执行中可中止（`Statement.cancel()`）

### W2 只读与写操作分流（必做）

这是工作台的核心逻辑，也是它区别于「一个 SQL 输入框」的地方：

| 语句类型 | 行为 |
|---|---|
| SELECT / WITH / SHOW / DESC / EXPLAIN | 直接执行，返回结构化结果 |
| UPDATE / DELETE / INSERT | **不直接执行**，走预检 → 生成任务 → 提交审批中心 |
| DDL | 走 `validate-ddl` 预检，再提交审批 |
| 别名标了 readonly | 一律拒绝写操作，提示改配置 |
| `accessMode=yearning` | 只读放行，写操作拒绝（Yearning 的设计边界就是只查询） |

按钮文案必须跟着变：只读语句是「执行」，写语句是「提交审批」——
让用户在点之前就知道会发生什么。

### W3 结果区（必做）

- 复用 `ResultTable`
- 行数 / 耗时 / 是否截断
- 导出 CSV（前端直接生成，不走后端）
- 多结果集分标签（`allowMultiQueries=true` 的连接可能返回多个）

### W4 与图谱联动（必做，这是差异化价值）

- 知识图谱页表详情加「在工作台查询」，带着 `SELECT * FROM schema.table LIMIT 100` 跳过去
- 编辑器里输入表名时用图谱索引补全，候选项显示业务描述而不只是表名
- 结果列头 hover 显示该字段的业务描述和语义类型

第三条是真正让"图谱"产生复利的地方：查出来的列不再是 `f_stat_1` 这种天书。

### W5 历史与重放（必做）

- 侧栏列出当前 alias 的 `sql_execution` 记录，点击回填到编辑器
- 与运行记录页共用数据源，但这里是「拿来改」而不是「看执行了什么」

### W6 安全约束（必做，不可省）

- 复用现有 WHERE 子句校验（无 WHERE 的 UPDATE/DELETE 直接拒绝）
- 最大返回行数、查询超时、单次单语句 —— 全部配置化（批次 4 已列此项）
- SM4 加密列的透明加解密沿用现有 `Sm4SqlCipherParser`
- 每次执行落 `sql_execution`，写操作额外落 `task_run`

### W7 后置（不排期）

多标签页、结果集图表、SQL 格式化、执行计划可视化。
都是"有更好"而不是"没有不行"，等工作台真被用起来再看哪个先被要求。

## 交付顺序

W1 + W2 + W3 + W6 是最小可用，约 1 周（在批次 4 完成的前提下）。
W4 + W5 再一个批次，约 3 天。

# 三、审批中心

> **2026-08-22：已按更简单的形态落地，本章的任务队列设计作废。**
>
> 实际实现的是 `ApprovalGate`——**发起方阻塞等放行**，而不是「提交任务 → 离线审批 →
> 后台执行」。别名上三个开关（`approveQuery` / `approveUpdate` / `approveGraph`）打开后，
> CLI 就停在终端里等，UI 的请求就挂着，直到有人在评审页裁决；跨进程协调走 SQLite 的
> `approval_request` 表，等待方 1 秒轮询自己那条记录。
>
> 这样一来本章的多数条目自动消失：
> - **状态机 PENDING/EXECUTING/… 不需要**——等待方一直握着连接，批准即继续
> - **`sql_hash` / `policy_revision` 防篡改校验不需要**——语句在等待方内存里，
>   批的和执行的物理上就是同一份
> - **A6 回滚入口**仍然成立（回滚本身是写操作，走同一道闸门）
>
> 下面仍然有效的只有一件事：**A2 的预检信息**。现在审批页只看得到一段 SQL 摘要，
> 缺影响行数、命中规则、恢复 SQL 是否可生成——这是「预检把关」的实质，
> 已排在开发清单的 P2。以下内容作为那部分的设计参考保留。

## 先说清楚这个模块到底在做什么

sql-cli 是单机工具，操作者和审批者是同一个人。
所以这里的「审批」**不是权限控制，而是三件事**：

1. **强制冷静期**——写操作不能手一抖就执行，必须经过一次独立的确认动作
2. **预检把关**——在确认页上摆出影响行数、规则命中、恢复 SQL 是否可用，让人带着信息做决定
3. **可审计留痕**——谁、什么时候、基于什么信息批准了什么，全部落库

**据此明确不做**：多级审批、角色权限、审批人指派、会签、超时自动通过。
这些是多人协作场景的东西，在单机工具里做出来只会变成点三次「同意」的仪式。
真到了多人共享那一天（开发清单批次 8 的触发条件），是 Team Server 的事。

## 数据基础

`task_run` / `task_event` / `recovery_artifact` 三张表在批次 2 已经建好，等批次 4 接线。
表结构够用，不需要改：

- `task_run`：task_type、actor、alias、status、sql_hash、policy_revision、时间戳
- `task_event`：任务的状态流转事件，一条记录一次变更
- `recovery_artifact`：恢复 SQL 文件的路径与校验和

## 状态机

```
                 ┌──────────────┐
   提交 ────────>│   PENDING    │
                 └──────┬───────┘
              批准      │      拒绝
          ┌─────────────┴────────────┐
          v                          v
   ┌─────────────┐            ┌────────────┐
   │  EXECUTING  │            │  REJECTED  │
   └──────┬──────┘            └────────────┘
     成功 │ 失败
   ┌──────┴───────┐
   v              v
┌──────────┐  ┌────────┐
│ SUCCEEDED│  │ FAILED │
└──────────┘  └────────┘
```

补充规则：
- PENDING 超过 24 小时自动置 `EXPIRED`（不是自动通过，是自动作废）——
  隔天再批准很危险，数据早就变了，预检结论已经失效
- 批准时校验 `sql_hash` 与提交时一致，防止「批的是 A、执行的是 B」
- 批准时校验 `policy_revision` 未变，规则集改过就要求重新预检

## 功能清单

### A1 待办列表（必做）

三类对象合并成一个列表，按提交时间倒序：

| 类型 | 来源 | 关键信息 |
|---|---|---|
| SQL 写操作 | 工作台 / CLI 提交 | 语句类型、目标表、预估影响行数 |
| 图谱候选变更 | Agent 写入的 candidate | 变更对象、置信度、证据 |
| DDL 校验结果 | `validate-ddl` | 变更摘要、violations 数 |

支持按类型、alias、状态过滤。

### A2 SQL 任务详情页（必做，这一页决定整个模块的价值）

摆在同一屏上，让人一眼能判断该不该批：

- 原始 SQL（不脱敏，审批人有权看到全文）
- **预估影响行数**——用相同 WHERE 跑一次 `SELECT COUNT(*)`，这是最关键的一个数字
- 命中的规则与严重级别（来自 PolicyEvaluator）
- **恢复 SQL 是否已生成**：能回滚和不能回滚，是两种完全不同的风险
- 目标表的图谱信息：业务描述、关系、是否有下游依赖
- 执行计划（EXPLAIN，可选展开）

批准需要二次确认并填理由；拒绝必须填理由。

### A3 图谱候选审核（部分已完成）

批次 6 已经做了关系的发布/拒绝（在表详情的「待审核」分组里）。
审批中心这里补的是：

- 集中视图：所有 candidate 一处看，不用挨个点表去找
- 批量发布 / 批量拒绝
- diff 展示：候选值 vs 当前值
- 证据展示：Agent 是从哪个文件、哪段代码推断出来的（`RelationEvidence`）

### A4 执行与结果（必做）

批准后的执行必须满足批次 4 定的事务边界：
同连接重读 → 恢复文件先落盘并登记 `recovery_artifact` → 事务执行 → 记录结果。
任一步失败整体回滚。**「执行成功但恢复文件没落盘」这个窗口必须为零。**

执行结果回写 `task_run.status` 并追加 `task_event`。

### A5 审计视图（必做）

按时间线展示某个任务的完整历程：提交 → 预检结论 → 批准（谁、何时、什么理由）→
执行 → 结果。数据全在 `task_event` 里，这一页只是把它渲染出来。

### A6 回滚入口（必做）

对已执行成功且有恢复文件的任务，提供「生成回滚任务」——
注意是**生成一个新的待审批任务**，而不是直接执行回滚。回滚本身也是写操作。

## 交付顺序

A1 + A2 + A4 是一个批次（约 1 周），必须在批次 4 之后。
A3 + A5 + A6 一个批次（约 3 天）。

# 四、三个模块的依赖关系

```
驱动管理  ──────────────────────────>  可独立开工，无前置依赖
                                       
批次 4（SqlTaskModule + 结构化结果）
    │
    ├──> SQL 工作台 W1/W2/W3/W6
    │         │
    │         └──> W4（还需要图谱索引，已具备）
    │
    └──> 审批中心 A1/A2/A4
              │
              └──> A3/A5/A6
```

**建议开工顺序**：驱动管理（可以立刻做，且能马上减少新装用户的坑）→ 批次 4 →
审批中心 A1/A2/A4 →  SQL 工作台 → 各自的第二批次。

审批中心排在工作台前面，是因为工作台的写操作分流（W2）需要一个能接收任务的地方；
反过来先做工作台，写操作就只能先直接执行，等于把批次 4 刚消除的风险又放回去。
