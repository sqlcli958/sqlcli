# 图谱评估方案

## 0. 这份方案要回答的问题

**图谱的目的是让人和 agent 拿着它就能迅速做开发和决策。评估要回答的是：现在够不够，
不够在哪，差多少，改完有没有变好。**

不回答「图谱有多全」——那是虚荣指标。531 张表的描述覆盖率 60% 和 30%，对一个只用到
40 张表的人来说没有区别。

---

## 1. 判读口径：什么叫「够用」

一次评估产出三个数和一个计数，**不产出综合评分**（加权是拍脑袋，没有普适答案）：

| 指标 | 含义 | 判读 |
|---|---|---|
| **硬错误数** | 「无论如何都是错」的问题条数 | **必须为 0**，非 0 则评估失败（退出码 1） |
| **在用表覆盖率** | 被真实查询用过的表里，有业务描述的比例 | 只看趋势，不设阈值 |
| **检索命中率** | 评估集上的 Top1 / Top5 / MRR | 只看趋势，不设阈值 |
| **任务通过率** | 任务级评估集里一次做对的比例 | 唯一直接对应目标的数 |

**只有硬错误判失败。** 覆盖率类指标设阈值就是瞎设——「表描述覆盖 70% 算不算够」
没有普适答案，而硬错误（比如一条既没描述也没映射的术语）在任何项目里都是错的。

---

## 2. 一次评估怎么发生

```
触发
  ├── 人：sql-cli <alias> schema eval
  ├── agent：写回图谱之后自检
  └── CI：每次图谱变更后
        ↓
锁定被测对象：alias + 图谱 revision N（评估结果永远绑在一个 revision 上，否则没法对比）
        ↓
逐个跑探针 probe（见 §3），每个探针产出若干 finding
        ↓
结果入库：graph_evaluation（一次评估）+ graph_finding（每条问题）
        ↓
判读：硬错误是否为 0；三个指标与上一次评估的差
        ↓
修复：每条 finding 自带一条可执行命令，报告即工作队列
        ↓
复评：改完重跑，比对同一份评估集在 N 和 N+k 上的结果
```

**两个设计要点：**

**结果必须入库、必须绑 revision。** 跑一次打印一堆数字不叫评估方案，那叫体检报告。
能回答「这次比上次好了还是坏了」才叫。存储直接复用 `policy_evaluation` /
`policy_violation` 的模式（同样是「一次运行 + 一批违规」，同样有起止时间、状态、actor），
不新造一套。

**每条 finding 必须自带修法。** 一条只说「这个字段没有描述」的 finding 是抱怨；
一条说「这个字段没有描述，跑 `schema edit --column X --description ...`」的 finding 是任务。
评估报告的价值不在分数，在于它是一份**排好序的、可以直接交给 agent 执行的工作队列**。

## 3. 探针清单

每个探针 = 一个明确的问题 + 一个明确的判据 + 一个明确的修法。

### 3.1 硬错误（自动，无需标注，判失败）

| 探针 | 判据 | 数据来源 | 修法 |
|---|---|---|---|
| `term.orphan` | 术语既无 description 也无 term_mapping | 图谱 | `schema add-term X --description … --map …` |
| `term.cross-domain` | 术语别名把查询引向另一个域 | 图谱 + 检索 | 加 `negativeAliases` |
| `value.contradiction` | 库里存在 enumValues 声明之外的值 | 库 + 图谱 | `schema edit --enum-values …` |
| `desc.dead-ref` | 描述里提到的表/字段在图谱中不存在 | 图谱 | 改描述 |
| `rel.endpoint-mismatch` | 关系两端字段类型不匹配 | 图谱 | 复用 policy 的 `join_column_type_match` |

`term.orphan` 为什么是硬错误：空壳术语不是「少了点东西」而是**主动有害**。检索里术语
权重最高（`WorkspaceIndexedSearchEngine` 给 term 8 分档），一条没有内容的术语稳稳占住
Top1，把真表压低一名。实测：5 条空壳术语让 Top1 从 55.6% 掉到 11.1%，MRR 从 0.66 掉到 0.41。

判据的出处见 [图谱语义机制](graph-semantic-mechanisms.zh-CN.md)：术语要么挂 ≥2 个对象、
要么有同义词 / 负向词，两者都不满足就该写进 `businessName`。那份文档里的方案 C
（术语作查询扩展的路由器，不参与排名）如果落地，这条探针的严重性会下降——
空壳术语届时是「自然沉默」而不是「占住 Top1」——但探针本身仍然要留，它挡的是浪费。

### 3.2 改进项（自动，只报告不判失败，按影响排序）

| 探针 | 判据 | 数据来源 | 修法 |
|---|---|---|---|
| `cover.used-table` | 被查询用过、但没有业务描述的表 | 执行历史 + 图谱 | `schema edit --table …` |
| `value.dead-column` | 分布极度倾斜（单值 >99%）或全 NULL | 库 | 标 deprecated，或明确写「未启用」 |
| `rel.missing-join` | 执行历史里常一起 JOIN、图谱里却没有关系 | 执行历史 + 图谱 | `schema add-relation …` |
| `rel.isolated` | 一条结构关系都没有的表 | 图谱 | 补关系或确认它本就独立 |

**排序按「影响面 × 修复成本」**：一张被查过 50 次的表没描述，排在一张从没被查过的表前面。
影响面直接取执行历史里的出现次数——这是把「哪些该先补」这个判断交给真实使用，
而不是交给人的印象。

### 3.3 需标注（评估集驱动）

| 探针 | 判据 | 评估集 |
|---|---|---|
| `search.miss` | 业务词的期望对象不在 Top5 | `search-eval` cases |
| `search.confuse` | 易混对象组里落到了错的那个 | 同上，按「区分组」编写 |
| `task.fail` | 任务级：产出的表集合/JOIN 与期望不符 | `task-eval` cases |

## 4. 值域：三源交叉生成

**不是拿库去校验图谱，是拿三个来源交叉生成一份可信的值域。**

| 来源 | 给出什么 | 可靠性 |
|---|---|---|
| **库里实际分布**<br>`SELECT col, COUNT(*) … GROUP BY col` | 真实存在哪些值、每个值多少行 | 是事实，但不含语义（不知道 `1` 是什么意思） |
| **字段注释**<br>`是否扫码 0=免扫码,1=必须扫码` | 值 → 含义 | 有语义，可能过期或不全 |
| **代码枚举**<br>Java enum / 常量 / Mapper XML | 值 → 名字 | 有语义，通常最新 |

三源比对之后落到四种结论，**每一种都是一个可操作的信号**：

| 结论 | 含义 | 动作 |
|---|---|---|
| 三源一致 | 值域确认 | 写回 enumValues，可标 verified |
| 库里有、注释/代码没有 | **注释过期，或有脏数据** | 查这个值哪来的；补进值域或当数据问题上报 |
| 注释/代码有、库里没有 | 该值从未使用 | 保留但标注「未出现」——测试库数据不全时很常见 |
| 分布极度倾斜（单值 >99% / 全 NULL） | **这个字段实际上没在用** | 明确写「未启用」，避免 agent 基于它做判断 |

第四条是这套交叉最容易被忽略、但对 agent 最有用的一条：它回答的是
「这个字段虽然存在，但不要用它来做判断」——只看 DDL 和注释永远得不出这个结论。

**采样策略**：`GROUP BY` 只对低基数列有意义。先 `COUNT(DISTINCT col)`，超过阈值
（建议 50）就判定为高基数列、跳过枚举分析，只记「非枚举」。这样一张表几十个字段
也只是几条聚合查询，不会打爆库。

**产出直接可写回**——这是全套探针里唯一一个「评估顺便把图谱补好了」的，
所以优先级最高。

## 5. 评估集：怎么来，怎么不烂尾

评估集要人写，写完就没人更新——这是这类方案唯一真正的死因。

**机制：让评估集从执行历史自己长出来。**

```
sql_execution 执行历史
   ↓ 挖出真实跑过的 SQL
   ↓ 抽出表集合 + JOIN 条件 + WHERE 里的业务词
候选 case（自动生成，标 pending）
   ↓ 人只做一件事：审核，改 expect
正式 case
```

人不需要凭空想「该测什么」，只需要对着真实用过的查询点头或改一改。skill 的
`references/execution-mine.md` 已经铺了一半的路（从执行记录回溯真实用过的 JOIN）。

两类评估集：

**检索评估集**（已有格式，`search-eval`）
```yaml
cases:
  - query: "巡检计划"
    expect: [table:alias:schema.table, ...]   # 任一命中即算
```
**编写规范**：易混对象必须成组写。单独测「巡检计划」只能测出「找得到」，
要测出「分得清」，必须把 `erp_prop_task_plan` / `erp_prop_task_point` /
`erp_prop_plan_point` 的三种问法放进同一批，每个只标一个正确落点。

**任务评估集**（新，见 `docs/task-eval-erp-inspection.yaml`）
```yaml
tasks:
  - id: …
    task: "自然语言任务"
    expect:
      tables: [必须用到的表]
      joins:  [必须走对的连接]
      pitfalls: [容易踩的坑：选错的那张表、值域陷阱]
```
`pitfalls` 是关键字段：它把「安静地出错数」这类失败变成可判定的。**每条 pitfall 必须带
`forbid`（不该出现的表/字段/写法，出现即踩中）或 `require`（必须出现的字段/条件，缺失即踩中）**，
只写 `desc` 的纯自然语言 pitfall 在解析时直接报错——判不了的判据等于没有判据。

### 怎么产出 answers.yaml

`sql-cli` **不跑 agent，只判分**。跑 agent 是外部 harness（Claude Code）的事：

```
对每个 case 起两个 agent，同一个 task 各跑一遍
  control  只给 sql-cli skill 和图谱（不给库的直连、不给答案）
  cheat    同上，外加把这条 case 的 expect.tables 抄给它（只藏 JOIN 和值域）
      ↓
把两个 agent 产出的表集合 / JOIN / SQL / 关键字段取值填进 answers.yaml
      ↓
sql-cli <alias> schema task-eval --cases <tasks.yaml> --answers <answers.yaml> [--json]
```

模板见 `docs/task-eval-answers.example.yaml`。报告按 §6.2 那张归因表分三段列
（图谱侧失败 / skill 侧失败 / 无法归因），末尾给通过率、图谱侧失败数、skill 侧失败数。
skill 侧失败会打印 case 上标注的 `skillRef`——该改的是 `skills/sql-cli/references/` 里的哪一份。

**为什么这条命令里没有 LLM**：判分是纯函数（两份 YAML 进、一份报告出），
所以它能进 CI、能复跑、结果可比。起 agent 那一步不确定、要花钱，不该混在评分器里。

**只填 `control` 也能跑**，但失败的 case 会全部落进「无法归因」并明说原因——
归因是整套方案里最值钱的一条，缺了它通过率就是个看了也不知道该做什么的数字。

## 6. 落地顺序

| 阶段 | 内容 | 需要标注 | 为什么这个顺序 |
|---|---|---|---|
| **L1** | 硬错误探针 + 值域三源交叉 | 否 | 全自动，抓的是不报错的错误，且值域那条顺带把图谱补好 |
| **L2** | 覆盖率 + 在用表加权 + CLI 入口 | 否 | 复用已有计算，agent 需要 CLI 入口自检 |
| **L4** | 检索评估集的「区分组」规范 | 是 | 不需要新代码，只需要改评估集写法 |
| **L5** | 任务级评估 | 是 | 最贵，但唯一直接测目标；先手工跑 10 个。**评分器已落地**（`schema task-eval`），起 agent 那一步仍是 harness 手工跑 |

L3（检索命中率）已经有了（`search-eval`），不单列阶段。

---

## 7. 边界

- **不做综合评分卡**：加权是拍脑袋。
- **不新起规则引擎**：能表达成 policy 规则的探针就进 policy。
- **`schema health/eval`（评图谱这份元数据）和 `schema policy`（评数据库设计规范）分开**：
  一个评元数据，一个评库，混进一份报告读的人分不清在说谁。
