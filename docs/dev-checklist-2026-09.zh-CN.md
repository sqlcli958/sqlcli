## 判断依据：语义层不是领域模型，但设计阶段是同一次决策

这一节是下面所有条目的理由，先写清楚，免得实现时又从头争一遍。

**三条硬区别：**

1. **写侧 vs 读侧。** DDD 的单位是命令——聚合根、不变量、事务边界，目的是让
   「订单不能被支付两次」在代码里不可能。语义层的单位是查询,它没有行为、没有不变量、
   没有事务;它有的是 DDD 从头到尾不谈的三个词:**基数、粒度、可加性**。
2. **边界判据不同，且会画到不同地方。** DDD 按「哪些东西必须在一个事务里一致」切；
   语义层按「哪些数可以加在一起而不重复计数」切。订单 / 订单行:DDD 说是**一个**聚合,
   语义层说是**两个**不同粒度的事实表——join 起来 `SUM(order.amount)` 直接算大
   （扇形陷阱,见 `MetricRecord.java` joinPath 字段注释）。同一组实体,两套模型结论相反。
3. **发明 vs 考古。** 领域模型自上而下发明;语义层自下而上考古——表已经在那了,
   命名是十年前某个人拍的。所以语义层天生要处理不完整、有争议、置信度,
   这正是图谱有 `confidence` / `GraphStatus.candidate` / `RelationEvidence` 的原因。
   **一个带 confidence 的领域模型是荒谬的,一个不带 confidence 的语义层是在撒谎。**

**唯一真重叠**:DDD 的 Ubiquitous Language ≈ `TermWorkspaceNode`
（`aliases` / `negativeAliases` 就是带检索的统一语言词表）。这一层可以借 DDD 的话术,其余不借。

**但设计阶段确实是 DDD,而且平台已经坐在那把椅子上**（`schema design review --ddl`
+ `migration lint`）。关键的一句是:**设计阶段不产出语义层,它是产出语义层唯一免费的时机。**

| 一次设计决策 | 输出到哪 |
|---|---|
| 聚合边界、不变量、事务边界（DDD） | DDL:表边界 / FK / 唯一约束 / NOT NULL |
| 粒度、事实还是维度、可加性（语义层） | 图谱注解 |

你按聚合根把订单行切出来的**同一秒**,就已经知道「一行代表一个订单商品」「它是事实表」。
此刻这条信息是零成本副产品;等表上线三年后再问就是考古,而且多半问不出来。
**真正的缺口不是「要不要有设计阶段」,是设计阶段只收了一半产物**——`CandidateDdlProjector`
投影出的 `TableWorkspaceNode` 里 grain / 角色 / businessName 全是空的,因为 DDL 里没地方写。

**边界（别越过去）**:不要在平台里建聚合根 / 实体 / 值对象这套模型对象。一,判断聚合边界
要看业务代码和用例,平台看不到,做出来只能靠人手填一遍、填完没人维护;二,DDD 模型的价值
在于约束写路径的代码,不在库里,库里留下的只是它的影子。而那道影子恰好就是 `design review`
**已经在查的东西**:表边界、FK、唯一约束、非空。已经在做 DDD 里唯一能被数据库验证的部分了,
不要往上加。

## E1 交付说明（做的过程中改了三次判据，都记下来）

`gated` 那个 boolean 换成了 `ApprovalMode{AUTO,NEVER,ALWAYS}`——三种语义装不进一个布尔。

**判据错了三次，每次都是在真库上跑出来的，三条都有回归测试：**

1. **绝对基数当成了枚举判据。** 直接用了 profiler 的 `lowCardinality`（distinct &lt; 50）。
   在一张 39 行的表上**每一列**都满足——UUID 主键、计划名称、创建时间全被当成枚举，
   35 列报出 31 条「发现」，25 条是垃圾。
   改成**相对**基数 `distinct/nonNull ≤ 0.1`，它天然随表规模缩放。
2. **序号和版本号漏网。** `sort`(1~17)、`version`(乐观锁) 相对基数够低。
   判据其实模型自己写过——`ColumnValueHints` 注释：「值多到不该内联的（字典表）不在这里」。
   加了取值个数上限 8。
3. **差点毁掉人工整理的成果。** 只把注释和代码当语义源，漏了**图谱已有的值域**。
   `is_scan` 注释只有「是否扫码」而图谱里已写好 `0=免扫码,1=必须扫码`，
   提议是把标签冲成裸的 `['1','0']`，还误报成一条发现。
   图谱已有的是**人批准过的第四个源**，按「图谱已有 → 注释 → 代码」叠加。

   > **这一条是审批机制救回来的**：提议全程没碰图谱，发现问题时撤回即可。
   > 如果 E1 当初设计成直接写回，这次就是一次静默的数据损坏。

**已知没做的**：
- 分布倾斜只判到「非空行全是同一个值」。`ColumnProfile` 不带每个值的计数，
  测不了「99% 集中在一个值」。要做得扩 profiler，暂不做
- 「整列全 NULL」这类发现**没有落点**——没有值域可写就提不出审批，
  命令会明说有几条只报告不提交。正式归宿是 E2/E3 的 finding 表

## T3 · 术语改为查询扩展的路由器（待拍板）

- **层**：语义层
- **产出**：agent / 人写术语 + `--map`

      ⌘ 命中术语「巡检计划」— 一次周期性巡检任务的配置模板

## T4 · `add-term` 写入闸门（待拍板，breaking）

- **层**：语义层的写入约束
- **产出**：不产出，是对 `add-term` 的入参校验
- **消费**：不被消费——它是**闸门**，价值在于让不合格的东西写不进来
- **它挡的错**：空壳术语被写进图谱（先关水龙头，再擦地板）

- [ ] 不带 `--map` **且**不带 `--aliases` → 直接报错，报错里给出
      「你应该改用 `schema edit --business-name`」
- **判据**：术语要么挂 ≥2 个对象（一词多物），要么有同义词 / 负向词（多词一物）。
      两者都不满足时它与 `businessName` 完全重叠，而且更差——多一个对象要维护，
      还占着检索最高权重档
- **为什么是闸门而不是只靠评估探针**：先关水龙头，再擦地板。
      `erp_plush_test` 那 5 条空壳如果有这条闸门，压根写不进去
- **breaking**：会让 Agent 现有的 `add-term` 写法直接失败

## 现有 5 条术语的处置（等 T3/T4 定了再动）

| 术语 | 判据 | 结论 |
|---|---|---|
| 巡检计划 | 一词多物（3 张表） | 保留，挂 3 个 + 标主表 |
| 巡查点位 | 一词多物（配置态 / 执行态） | 保留，挂 2 个 + 标主 |
| 检查项 | 一词多物（标准 / 结果） | 保留，挂 2 个 + 标主 |

## 明确不做

- **把术语合并进 `businessName`**：1:1 的东西不能用 1:N 的结构存
  （10114 个字段就是 10114 个术语对象），反之亦然。它们是同一问题在两种基数下的两种正确形态
- **把术语合并进 `description`**：对象不同，不是详略之分——
  `term.description` 定义业务概念（不提表也说得清），`table/column.description`
  说的是「这个数据位置怎么回事」（必须提这张表）
- **现在拆 `term_mapping` 出 `relations` 集合**：它跟 `foreign_key`/`join_observed`
  确实不是一类东西（一个是「词指向什么」、一个是「数据怎么连」），代码里已有特判为证
  （`WorkspaceCompletenessDto`：`continue; // 结构健康只看表间关系`）。
  但拆出去要动模型和落盘格式，**记债不还**

# 方向记录 · 图谱存储：文件 vs DB

> **来源**：2026-08-28，「有些数据存 db 是不是会提高查询速度，后面尽量设计到 db 中」。
> 记录成方向，**当前不触发**——下面的实测把「更快」这个前提推翻了一半。

## 实测（2026-08-28，`erp_plush_test`：531 表 / 10114 字段 / 89 关系）

5 次取最小值：

| 命令 | 最小耗时 |
|---|---|
| `schema stats`（**加载整个图谱**：531 个 YAML + 3 个 jsonl） | 940 ms |
| `sql-cli list`（**不加载图谱**，只解析别名/驱动/密码） | 1,068 ms |
| `app` 查 SQLite（JDBC 一次 COUNT） | 1,151 ms |

**加载整个图谱比不加载还快，净成本是负数**——它完全淹在 JVM 启动（约 1 秒）以下。
**当前规模下文件解析不是性能问题，把它搬进 db 不会让任何东西变快。**

## DB 真正的优势在别处，不在「快」

1. **能只读需要的那部分。** 现在「血缘总览分页」「哪些字段没描述」「按 schema 筛表」
   都必须全量 `load()` 再在内存里过滤。这才是文件布局真正的天花板——不是单次读取慢，
   是**没有办法只取一部分**。
2. **并发写。** 文件 + `WorkspaceLockManager` 写锁 vs SQLite WAL。

## 代价（CLAUDE.md 记过的两条，搬进 db 就没了）

- 图谱能**整目录 export / import 搬走**（`generations/` 是那个载体）
- 图谱能**进 Git 做 diff**

## 结论：文件是权威源，db 是派生索引

不搬本体，需要「只取一部分」时**加一层可重建的 db 投影**——跟搜索索引 `index/`
（留文件、随时可 rebuild）是同一个模式，只是换成 SQLite 表。这样查询能力和
export/import + git diff 两边都保得住。

投影是派生的，所以：**任何时候删掉重建都不丢数据**，这条必须成立，否则它就变成了第二个权威源。

## 什么时候动（触发条件，别提前做）

满足任一条：

- 单次 `GraphWorkspaceStore.load()` 超过 **300 ms**（当前 < 100 ms，按表数大致线性外推
  约 3000 张表触发）
- 出现一个**必须分页 + 服务端过滤**的图谱列表（现在血缘总览是整份返回、前端切页，
  见 `handleLineageOverview` 的 ponytail 注释；再多几个这样的地方就是信号）
- UI 的 `refreshWorkspace()` 成为可感知的卡顿（它**每个 mutation 请求都重新加载一次**）

## 顺带记一笔已知的浪费

`WorkspaceMutationService.stageForApproval` 为了拿 `before` **额外 load 了一次工作区**
（已带 ponytail 注释）。开了图谱审批的别名上每次写入是两次全量加载。
当前无感，但触发条件满足时这里是第一个要改的点。

# 审批管线统一与批量提交（A1~A6）· 已完成 2026-08-30

完整推理见 [审批管线统一与批量提交](approval-batch-design.zh-CN.md)（含三处与原方案的偏差）。

  ③ 图谱改了但追不到「谁、哪次会话、为了什么」（今天 `graph_change_log` 只有

## 交付说明（做的过程中撞到的三件事）

1. **`query_convention` 加进 `RuleSetLoader.CATEGORIES` 之后必须同时在 `PolicyEvaluator`
   的 switch 里显式跳过**，否则任何绑了约定规则的工作区跑 `policy check` 会撞上
   `default -> throw`，报「unknown rule category」。约定规则不产出违规，它是 policy 的
   第二个消费者。
2. **删除术语不做级联。** 审批 payload 是单对象补丁，在删除里顺手删掉 `term_mapping` 边，
   在 `manual` 别名上批准时重放的只有术语那一条——边会留下来变成
   `dangling_relation_source` 校验错误，**而且是批准之后才出现**。所以还挂着映射就拒绝删，
   报错说清剩几条。要一步到位得拆成批次，不是在这里级联。
3. **`describe --json` 的键从 5 个变成 7 个**（`conventions` / `scenarios`），
   `JsonContractSnapshotTest` 会挡住，这是有意的契约扩展。只出现在文本输出等于 agent 拿不到。

**S5 是批次能力的第一个真实用例**：一个 intent、9 个条目、人一次审完，
顺带验证批次与部分批准是否真好用。

# D1 · `describe` / `search` 输出改造（2026-09-03，本轮第一个闭环）

> 拍板见 [产品方向拍板记录](product-direction-2026-09-03.zh-CN.md) 第三节第 5、8、9、10 条。
> **F5 和 E4 都改道到这里**，按新的验收单位合成**一次**交付——三件事落在同一个输出上，
> 拆开就是再演一遍 F5 的死因。

- **层**：语义层（第 1、3 项）∩ 结构层（第 2 项）
- **产出**：不产出，纯消费方——它把图谱里已经躺着的东西放进 agent 看得见的地方
- **消费**：**agent 开工前那一刻**，判断这张表能不能直接用、信到什么程度
- **它挡的错**：① agent 拿着一份 0.4% 的图谱当权威，**不报错**；
  ② `SUM` 被 join 乘大，SQL 照跑数字照出；③ 图谱与代码分叉后 agent 无从察觉——
  **产品的价值主张是让 agent 不必读代码，所以图谱越被信任、错的时候越贵**

## 三项内容

- [x] **1 · 表级一行完整度**（原 E4）。`describe` 顶部一行，`--json` 里是 `completeness`
- [x] **2 · `grain` + 关系基数注入**（原 F5）。表头带 `grain`，关系每条带基数，
      本表处在 ≥2 条一对多的「一」侧时额外提示扇形陷阱
- [x] **3 · `describe --column <列>` 展开单列**：格式 / 示例值 / 默认值 / 置信度 /
      有没有人复核过。同时**不再打印整表**——预算就是这么省下来的
- [x] 技能同批改：`query.md` 新增「先看第一行」「Grain 和关系基数」「单列追问」三节。
      **不写技能 = agent 不知道该怎么读它，功能还是死的**

## 做的过程中改了两次判据，都是在真库上撞出来的

1. **「有没有人整理过」不能看 `updatedBy`。** 原设计拿 `updatedBy ∈ {agent, human}`
   当整理痕迹，实测 `erp_prop_report`——被 agent 写满了描述、值域和 grain——它的
   `updatedBy` 是 **`system`**：回写行数那次记账把 actor 盖掉了（CLAUDE.md 里
   system 的记账动作就包括「回写行数」）。**拿 actor 当判据会把做透的表报成
   「从未有人补充」，正好把这条提示的唯一用处反过来。** 改成看内容：
   表或任一列有 description / businessName / valueHints / grain 就是被整理过。
   > **顺带记一笔债**：`updatedBy` 现在表达不了「谁最后动了业务语义」，
   > 记账动作和内容变更共用一个字段。要区分得给记账动作单开一列，暂不做。

2. **关系基数几乎全是 `unknown`，不推断的话这条路径是死的。** `erp_prop_report`
   的 14 条关系基数**一条都没填**（全库 128 条里 57 条 unknown）——agent 写
   `add-relation` 时基本不填它。所以加了一条推断：**指向主键或唯一列的那一端是「一」**，
   只读 DDL 已声明的约束，不猜业务，推断出来的标 `(推断)`（跟 `schema path` 的
   `INNER JOIN（推断）` 同一个写法）。推断后 14 条里 13 条定了向，扇形陷阱提示才第一次触发。
   > 验证：`erp_prop_report` 报出「处在 2 条一对多关系的「一」侧」，
   > 而这张表的人工描述里写着「派单/处理/回访三类动作各自在 erp_prop_report_assign
   > 落一条子单，按报事聚合时要对 report_id 去重」——**自动检测和人写的警告对上了。**

**回归测试**：`SchemaDescribeCompletenessTest` 四条（内容判据 / 未整理表 / 基数推断 +
扇形陷阱 / 单列不打整表），`JsonContractSnapshotTest` 的 describe 契约从 7 键扩到 8 键。

## 上下文预算：为什么第 3 项不进全表输出

`describe erp_prop_report` 现在是 **92 行 / 9075 字符**（63 列 + 13 关系）。
修一个 bug 要 describe 三五张表就是 1 万 token 打底，逐列出处会让它翻倍。

**两个需求的粒度本来就不同**：第 1 项回答「这张表的语义能不能信」——**一行就够**；
第 3 项是 agent **已经决定要用某条语义之后**的追问，是单列粒度。
混进一份输出等于**每次全表输出都替一个可能不会发生的追问付费**。

## 验收：双向，缺一边不算

- 在 agent **没干过**的域（设备 / 仓储），开工前要能判断出「这块不够，我得先读代码」
- 在**已经做透**的报事域，要能**不读代码直接用图谱**

> **单向验收是个陷阱。** 只测第一个方向，最省事的通过方式是让 agent 永远说
> 「不够，去读代码」——那和没有图谱一样，还多花了 9075 字符。
> **第二个方向才是这个产品的价值证明**，它测的是省下的那次代码阅读。

# P1 · `schema policy` 作用域收窄（2026-09-03）

> 拍板见 [产品方向拍板记录](product-direction-2026-09-03.zh-CN.md) 第三节第 6 条。

- **层**：结构层的质量检查
- **产出**：不产出，是对现有规则集作用域的收窄
- **消费**：**人**——收窄之后这份报告才第一次可能被读完
- **它挡的错**：**一份没人能执行的报告和没有报告是一样的**

**实测**：最后一次运行 2026-08-21，**1487 条违规，其中 1215 条 `naming_convention`**，
豁免 0 条，之后无人再跑。那 1215 条跑在一个十年前的遗留库上——**那些表名永远不会改**。

- [x] 默认只对 `design review` / `migration lint` 的**新 DDL** 生效；存量全量检查要显式开
- [x] 全量检查里**命名类规则默认关闭**，只留 `money_type_decimal`（218 条，真能修）
      和 `sensitive_column_policy`（54 条，合规相关）
- **为什么不是「靠豁免机制消化」**：十天零豁免已经证明它不会发生

> **这条要先于 E2/E3 落地。** `schema eval` 的 finding 表会原样复现这个结局，
> 所以 E3 的数量闸门（见下）判据就是从这 1215 条读出来的：
> **当一类 finding 的数量超过人能处理的量级，它报的不是「图谱错了」而是「规则用错了对象」。**

## 落地：一个字段（`PolicyRule.scope`）+ 一个临时开关（`--all`）

`scope: change | all` 写在规则上，`RuleSetLoader` 按类别兜底：**只有 `naming_convention`
默认 `change`**，其余默认 `all`。`defaults.scope` 可以整份规则集统一指定，
`policy check --all` 是「这一次全查」的临时开关。**没有新增命令、没有新增存储。**

**收窄是两半，只做一半等于没做**：

| 半 | 落在哪 | 不做的话 |
|---|---|---|
| 全量检查跳过 `scope: change` 的规则 | `PolicyEvaluator.runs` | 就是今天这 1215 条 |
| **review 只查这次 DDL 碰到的表** | `PolicyEvaluator.changedTables` + 每条规则跑完按表过滤 | 噪音从 `policy check` 原样搬到 `design review`——候选工作区是「整个图谱 + 新 DDL」，命名规则照样在 499 张遗留表上跑一遍 |

按**表**过滤而不是按对象：`table:` / `column:` / `table:...:index:...` 都归到
`alias:schema.table`；取不到表的 id（关系 id、SQL 的来源引用、图谱里没有的表名）一律放行——
它们的判据来自送进来的 SQL 或变更集本身，按表过滤会把 `dangerous_dml_guard`
自己的结论吃掉。

`evaluatedRules` 改成**实际跑了几条**，`PolicyCheckResult.skippedRules` 是跳过的条数，
文本输出里点名说「跳过 N 条」——不说的话「0 条违规」和「这条规则根本没跑」长得一模一样。

**回归**：`SchemaPolicyCommandTest.namingRulesSkipTheLegacyGraphUnlessAllIsRequested`
（默认 0 条 → `--all` 出 → 规则里写 `scope: all` 也出）、
`designReviewReportsOnlyTheTablesTheDdlTouches`（存量表同样缺主键但不报）。

## W1 · `ProfileGraphWriter` 接上消费路径（P2）

- **层**：结构层（关系的可选性）
- **产出**：`TableProfiler` 的实测空值率——**它已经在跑了**，`schema value-domain`
  每次都会剖析整表，这份数据是白拿的
- **消费**：`schema path` 的 `INNER JOIN（推断）` / `LEFT JOIN（推断）` 判断
- **它挡的错**：外键列声明可空、实测空值率却为 0 时，`INNER JOIN` 是安全的；
  只看 `nullable` 声明会一律给 `LEFT`，**多查出一批本该被过滤掉的行**。
  反过来声明非空而实测有空值时，`INNER` 会**静默丢行**——不报错、有结果、数偏少

- [x] `ProfileGraphWriter` **零生产调用**：全仓只有 `ColumnWorkspaceNode` 的一句 javadoc
      提到它，加上它自己的测试。E1 当初写着「给 `com.sqlcli.profile` 接上消费路径」，
      实际接上的是 `TableProfiler` / `ColumnProfile`（`ValueDomainCrosscheck` 走的是
      另一条新路），**这个写回器被落下了**
- [x] 三件产出里**只接 optionality 那一件**：值域候选已被 `schema value-domain` 的三源交叉
      取代（那条路更准，多一个代码枚举源），标注质量告警的归宿是 E3 的 finding 表。
      **不要三件一起接**——接了会出现两条写值域的路径，正是「一个别名只能有一种行为」禁的东西。
      另外两件的代码**已删**（连同它们的测试）：留着不接就是这条本身
- [x] 落点是现成的：把 `optionalitySource` 从 `inferred`（只看 nullable 声明）升级成
      `profiled`（看实测空值率），key 复用 `RelationWorkspaceEdge.ATTR_*`，不新增字段
- **碰**：`SchemaActionCommand.valueDomain`（剖析已经在这里跑完了，顺手调一次）
- **验收**：一条声明可空但实测零空值的外键边，`schema path` 从 `LEFT JOIN（推断）` 变成
  `INNER JOIN（推断）`，且 `optionalitySource` 是 `profiled`
  （`SchemaValueDomainOptionalityTest`，喂手搭的剖析结果，不连库）
- **要么接上，要么删掉。** 留着不接就是这份清单反复在说的那件事的第六个实例

### 做的过程中定的三件事

1. **写回不许自己写工作区，要走 `mutate`。** 原来的 `ProfileGraphWriter.writeBack` 直接
   改内存里的 `GraphWorkspace`——那是在管线外面开的一个口子，要不要审批由它自己说了算。
   改成**只算不写**：产出一串 `OptionalityUpgrade`，落地由 `valueDomain` 走
   `WorkspaceMutationService.mutate`，manual 别名照样排队，auto 别名当场落地。
2. **「实测零空值」要求采样覆盖整表。** 默认采样 10000 行。拿一千万行表的一万行样本断言
   「这列没有 NULL」再把 LEFT 改成 INNER，**正好造出这个功能要防的那种错**——
   不报错、有结果、数偏少。所以只有 `nullRatio > 0`（一个反例就够）不需要全表，
   `nullRatio == 0` 必须 `rowsSampled >= rowCount`，行数拿不到也不放行。
3. **`schema path` 的括号里现在分「推断」和「实测」。** 不分的话这条链路做完了 agent 也
   看不出区别：值翻了，可信度没传过去。`PathSegment` 多一个 `optionalitySource`，
   反向边跟着翻转时一起带过去。技能 `query.md` 同批改。

**顺手修的一个既有 bug**：`proposeValueDomains` 每条都用命令手里那份工作区的 revision，
而 `mutate` 落盘会把 revision 顶上去——auto 别名上一次提两条以上时，第二条必撞
`revision mismatch`。加了 `syncRevision`，两个 propose 循环共用。

## P6 · 数据层质量探针 `schema data-quality`（已完成）

- **层**：**数据层**——三层三套工具里空着的那一格，现在填上了
- **产出**：人或 agent 在重构前手动跑一次（连库、要授权，不进任何自动流程）
- **消费**：**agent 在决定「这个字段能不能删 / 这条边能不能 INNER JOIN」的那一步**读
  finding 表；每条 finding 自带命令，直接执行
- **它挡的错**：agent 拿一个实际没在用的字段（全 NULL / 99% 单值）当判断依据、
  按图谱声明的值域写 `WHERE ... IN` 而库里另有取值、按一条有孤儿的外键写 INNER JOIN
  静默丢行。这三件**代码永远查不到答案**——代码只能说有没有人写这行，不能说这行还跑不跑

- [x] **不并进 `schema eval`**。判据是「连不连库」：`eval` 纯计算毫秒级，这条要往库上打
      几百条聚合。合成一个命令的结果是同一个命令名两种代价，没人敢在生产别名上跑它
- [x] 四条探针，都是重构决策的直接输入：

  | 探针 | 判据 | 严重度 |
  |---|---|---|
  | `data.column-unused` | 整列全 NULL，或非空值 ≥99%（`DOMINANT_VALUE_RATIO`）是同一个取值 | warning |

  | `data.orphan-fk` | 图谱里 **verified** 的关系边，from 端非空值在对端找不到的比例 > 0 | warning |
  | `data.table-dead` | 行数为 0，或 `create_time` 类列的最大值早于 N 个月（默认 12，`--months`） | warning |

- [x] **只有 `enum-undeclared` 是 error**：其余三条是「值得看」不是「一定错」——
      99% 单值也可能是刚上线还没铺开的功能。而按错的值域写 WHERE 和 E1 一样是静默错误
- [x] **判据一律相对**（E1 交付说明第 1 条那个教训）：阈值全是比例，天然随表规模缩放。

      常量，不各写一个数字）和「多少个月算死」，后者是参数不是判据
- [x] **补上了 E1「已知没做的」第一条**：`ColumnProfile` 加 `topValue` / `topCount`，

- [x] `enum-undeclared` **不重写判据**，整个借 `ValueDomainCrosscheck.cross`（注释和代码枚举
      都不传——这条问的就是「图谱里写的够不够」，注释里补过的值救不了按图谱写 SQL 的 agent），

# W2 · task-eval 跑法 · 交付说明（2026-09-03，评分器已落地）

任务级评估集（`docs/task-eval-erp-inspection.yaml`，10 个任务）写完就躺着，没有跑法。
这条补的是**跑法里的判分那一半**。

- **层**：不属于三层里的任何一层——它是**评测**，测的是三层加起来够不够 agent 干活
- **产出**：外部 harness（Claude Code）对每个 case 起两个 agent（`control` 只给图谱、
  `cheat` 额外给正确表集合），把产出填进 `answers.yaml`
- **消费**：`sql-cli <alias> schema task-eval --cases <tasks.yaml> --answers <answers.yaml>`
  判分并归因，报告分三段：图谱侧失败 / skill 侧失败 / 无法归因
- **它挡的错**：① 通过率是个无法归因的数字，看了不知道该补图谱还是改 skill
  （[概念边界](graph-concept-boundaries.zh-CN.md) §6.2）；② 只比表集合和 JOIN 测不出
  「选错了名字相近的那张表」——那种 SQL 照样能跑、照样出数

## 定死的边界

**Java 里不调 LLM。** 起 agent 是 harness 的事，`sql-cli` 只吃两份 YAML 判分。
判分是纯函数，所以能进 CI、能复跑、结果可比；把不确定又花钱的那一步混进评分器，
这两条全没了。

**pitfall 必须可机判。** 每条 pitfall 除 `desc` 外必须带 `forbid`（出现即踩中）
或 `require`（缺失即踩中），只有自然语言的直接在解析时报错——判不了的判据等于没有判据。
现有 10 条已全部改成这个形状。匹配前两边去空白转小写，`is_scan = 0` 与 `is_scan=0` 同义。

# L1 · 字段血缘重新设计（2026-09-08，已拍板，同日实现）

> 起因：核对 `erp_plush_test` 的 12 条血缘时，一版按「有表达式的推导」判掉了 9 条。
> 对照 OpenLineage 列级血缘规范（DIRECT: IDENTITY / TRANSFORMATION / AGGREGATION；
> INDIRECT: JOIN / FILTER / GROUP_BY / SORT / WINDOW / CONDITIONAL）与 Apache Atlas
> （SIMPLE / EXPRESSION / SCRIPT），**原样拷贝和只决定写不写的列都算血缘**，那 9 条里
> 8 条是对的，只有 `result_value` 自指那条错。错判的根因不是那 12 条，是模型里没有类别：
> 一条「target ← sources」说不出是抄的、算的、汇总的还是按条件写的，读的人只能猜。
>
> 另一件事同时成立：概念边界文档把血缘判为「价值密度最低，暂停投入」，那是在
> 「查询数据」目的下写的。09-03 目的收窄成修 bug / 重构之后没有重判——
> 「改这个字段哪些下游值会跟着错、改动在哪个方法里」只有血缘答得出，`through` 指的就是那个方法。

- **层**：语义层（血缘本身），消费落在结构层的 `describe` / `search` 输出
- **产出**：agent 读代码，`add-lineage --kind`；UI 不新增不编辑，只删
- **消费**：`search` 命中列时的类别后缀；`describe` 表级每列后缀 + 下游计数；
  `describe --column` 的上游细节与**下游影响列表**；`schema lineage` 输出类别
- **它挡的错**：① 拿快照当当前值查（identity）；② 改了源列的语义或值域，
  下游写入静默失效，代码不报错（rule）；③ 汇总列与明细漂移仍被当事实（aggregation）

## 四个类别的职责

| kind | 定义 | 判据（代码里长什么样） | 字段约束 | agent 读到后的决定 | OpenLineage |
|---|---|---|---|---|---|
| `identity` | 值从一列原样抄来 | `b.setX(a.getX())`、INSERT SELECT 同名列 | 恰好 1 源，禁止 expression | 这是快照可能过期，当前值去权威源；改源列要同步改抄写代码 | DIRECT / IDENTITY |
| `transformation` | 同一行内由若干列算出 | `prefix + date + seq`、CASE 三选一 | ≥1 源，expression 必填；CASE 的选择列进 sources | 别手动重算，公式在 expression；值不对去 through | DIRECT / TRANSFORMATION |
| `aggregation` | 多行汇总出一个值 | 遍历子表算结论、SUM / COUNT / GROUP BY | 同上 | 冗余汇总可能与明细漂移，核对时按 expression 重算 | DIRECT / AGGREGATION |
| `rule` | 值不来自任何列（NOW / 常量 / 用户输入），列只决定写不写 | `if (all(...)) b.setEndTime(now())` | ≥1 源，expression 写规则原话 | 改源列的语义或值域会让这处写入静默失效；先看 through | INDIRECT / CONDITIONAL |

**关系与血缘可以并存于同一对列。** 关系答查询时行怎么对上，血缘答写入时值从哪来；
判据是有没有一段代码在写——血缘有 `through`，关系没有。

## CLI

```bash
sql-cli <alias> schema add-lineage --target <schema.table.column> --source <ref>[,<ref>...] \
    --through <TEXT> [--kind identity|transformation|aggregation|rule] [--expression E] [--confidence N]

sql-cli <alias> schema remove-lineage --target <schema.table.column> [--through TEXT]   # 该列只有一条时直接删，多条列出让你挑
sql-cli <alias> schema remove-lineage --id lineage:...                                  # 给 UI 和 --json 输出用

sql-cli <alias> schema lineage <schema.table.column> [--upstream|--downstream] [--depth N] [--json]   # 参数不变，每条加 kind；--json 加 openLineage
```

`add-lineage` 写入闸门，全部退出码 1 且给出改法：

| 情况 | 结果 |
|---|---|
| 源含目标本身 | 拒收：列不是自己的上游 |
| `identity` 多于 1 源或带 expression | 拒收，提示改 `transformation` |
| `transformation` / `aggregation` 无 expression | 拒收 |
| `rule` 无源 | 拒收，提示改用 `schema edit --description` |
| 缺 `--through` | 拒收 |
| 目标或任一源列不在图谱 | 拒收（现有行为） |

## 明确不做

- 血缘进 SQLite（拍板 1，触发条件见「图谱存储：文件 vs DB」）
- `--when` / 每个源列的 direct-indirect 标记（导出 OpenLineage 时再加）
- OpenLineage 的 JOIN / FILTER / GROUP_BY / SORT / WINDOW 单独成类
- 合并 `--redundant-of`（记债：identity 血缘数量超过冗余标注时再合）
- UI 新增 / 编辑血缘
- 自动从代码提取血缘
