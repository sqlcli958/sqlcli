## 一、前提变更：产品目的收窄

| | |
|---|---|
| 原来 | 给 agent 足够准确的上下文，让它能**设计数据库、梳理业务、查询数据、给用户准确的判断结论** |
| **现在** | 给 agent 足够准确的**数据库上下文**，让它能**修复 bug、重构业务代码** |

四个任务收成两个，而且从分析场景挪到了软件工程场景。**这一条决定了下面所有结论。**

**边界随之明确**：产品只负责**数据库这一侧**的上下文。代码那一侧——哪个文件调了哪个
Mapper、改这个字段要动哪几个类——**是 agent 的活，不是产品的活**。产品不做代码索引、
不做影响面分析、不存 `code_ref`。

- `schema policy` 最后一次运行 2026-08-21，**1487 条违规、其中 1215 条 `naming_convention`、

## 三、拍板记录

| # | 问题 | 定的 | 为什么不是另一个 |
|---|---|---|---|
| 1 | 产品主张选哪个 | **「让 agent 拿到的上下文不会骗它」**（值域 / `grain` / 关系基数 / 数据质量 / `schema eval`） | 「查询生成器」（metric + `query-plan`）的燃料是**人的口径知识**，实测 0 条 metric = 需求侧空转；本主张的燃料是**库和代码本身**，不依赖任何人先写内容 |
| 2 | metric 怎么处置 | **单开菜单、暂不开放**。只摘 UI 入口，存储仍留在 `GraphWorkspace` | 真搬出图谱要动模型、落盘、`GraphObjectPatch` 七类定位、审批 payload、change log，**是给一个不开放的功能预付结构成本**；且会丢掉 revision 乐观锁 / 候选态 / 评审 / 审计 / export-import 五样白拿的东西 |
| 3 | metric 的 CLI 和技能 | **CLI 留、技能里摘掉** | CLI 留着不碍事、有测试兜底、要试时是唯一入口；技能不摘的话 agent 每次都会先查指标、查到空、再回退，**多一跳且每次都白跑** |
| 4 | metric 什么时候重新开放 | **开启信号：出现一次真实的口径争议**（两次计算得出两个数且必须统一），照 08 文档 5.2 的「开启信号」格式写进清单 | 「功能完善后再说」没有边界，会变成这份清单里所有断裂共同的那个词——「等」 |
| 5 | F5 扇形陷阱怎么办 | **改道**：不在 `expand-metric` 里判，改成 `describe` / `search` 输出时把 `grain` + 关系基数注入给 agent | metric 不开放，F5 就成了「给一个不开放的功能做的检查」；改道后 `grain` 的读者从「一个展开器」变成「agent 每次 describe」，**消费方从机器变成 agent，而 agent 是唯一的真实用户** |
| 6 | `schema policy` 的作用域 | **收窄**：默认只对 `design review` / `migration lint` 的新 DDL 生效；全量检查里命名类规则默认关闭 | 1215 条命名违规跑在一个十年前的遗留库上，那些表名永远不会改。**十天零豁免已经证明「靠人去豁免」不会发生** |
| 7 | `schema eval` 怎么避免变成第二个 policy | **数量闸门 + finding 必须自带可执行命令**：单个探针产出超阈值就停止列举，改报一条「这个探针的规则用错了对象」 | 直接从那 1215 条读出来的判据：**当一类 finding 的数量超过人能处理的量级，它报的不是「图谱错了」而是「规则用错了对象」** |
| 8 | 「足够」由谁判定、什么时候判定 | **agent 自检**：`describe` / `search` 输出带上这张表的语义完整度 + 缺什么 + 上次谁什么时候补的 | 按需生长意味着任何时刻图谱都是部分完整的，而 agent 无法区分「没描述因为表确实简单」和「没描述因为没人干过这块」——**这两种情况下该做的事完全相反**。人工判定不能随库扩展也传递不给 agent；端到端评测是事后 |
| 9 | 图谱错了 agent 怎么知道 | **语义带出处和时效**：`describe` 显示每条语义来自列注释 / 代码 / 人工确认 + 时间 + confidence | 铁律 6（读代码发现不一致就当场改）依赖 agent 恰好读了代码，而产品的价值主张恰恰是让 agent **不必读代码**。**图谱越被信任，它错的时候越贵，且没有任何机制会发现** |
| 10 | 上下文预算怎么分 | **粒度分开**：完整度只加**表级一行**；逐条出处**不进全表输出**，只在 `describe --column` 追问单列时展开 | 一张表的 `describe` 已经 9075 字符。两个需求粒度本来就不同——完整度是「扫描时的判断」，出处是「使用时的核实」，混进一份输出等于每次全表输出都替一个可能不发生的追问付费 |
| 11 | 验收单位换不换 | **换成「一条闭环」**：一个交付必须同时含产出侧和消费侧，**不许把这两半切给两个 agent**；切不动说明它太大，该缩小闭环而不是拆成两半 | 现在按**改动面**切条目 + 并行 agent 落地，必然把产出和消费切开，而且每次都是消费那半留下。F5 的死因清单里写着：「被切给了两个不同的 agent，于是留成两边都完成后再补——然后就没有再补」 |
| 12 | 数据质量（数据形态）排哪 | **保持在规划里，随后做**。它回答的是重构最常问的三句：这个字段能删吗、这个枚举值还有人写吗、这张表还活着吗 | 这三句**代码永远查不到答案**——代码只能说有没有人写这行，不能说这行还跑不跑。E1 那条「单值 >99% 或全 NULL = 这个字段实际没在用」本身就是重构决策的直接输入 |

**复盘中提出并否掉的三个方案**，记下来免得再提：

| 方案 | 否掉的理由 |
|---|---|
| 放弃持久图谱，改成每次现场扫代码 + 现场查库 | 扫一遍的成本每次都付，而**人工修正没有地方存**。E1 那次「差点毁掉人工整理成果」证明人工修正是最高价值的一层 |
| 做静态代码扫描器批量生成语义 | 误把 0.4% 读成产能瓶颈。且 `code-scan.md` 列的四种易错情形（`<if>` 条件 JOIN 要降 confidence、别名还原、常量条件是关系的一部分、复合键是一条不是两条）**没有一条是 AST 能拿到的**——它们要求读者理解「这个 JOIN 在什么前提下成立」，解析器只能拿到语法，拿不到前提 |
| `schema impact <column>`（改字段影响哪些代码） | 把产品往代码侧拽。产品只管数据库这一侧，代码侧是 agent 的活 |

## 五、落地顺序

**第一个闭环：`describe` / `search` 的输出改造。** 上表第 5、8、9 三条落在同一个地方，
按第 11 条的规矩合成**一次**交付，不拆。

| | 内容 | 来自 |
|---|---|---|
| 1 | 表级一行完整度：多少列有描述 / 值域，最近谁什么时候补的 | 第 8 条 |
| 2 | `grain` + 关系基数注入 | 第 5 条 |
| 3 | `describe --column` 展开单列的出处与时效 | 第 9、10 条 |

**验收是双向的：**

- 在 agent **没干过**的域（设备 / 仓储），它开工前要能判断出「这块不够，我得先读代码」
- 在**已经做透**的报事域，它要能**不读代码直接用图谱**

> **单向验收是个陷阱。** 只测第一个方向，最省事的通过方式是让 agent 永远说「不够，去读代码」——
> 那和没有图谱一样，还多花了 9075 字符。**第二个方向才是这个产品的价值证明**，
> 它测的是省下的那次代码阅读。

之后的顺序：policy 收窄（第 6 条，纯收窄）→ `schema eval` E2/E3（带第 7 条的闸门）
→ 数据质量（第 12 条）。

> **2026-09-03 结算**：以上全部交付并合入 `direction-2026-09-03`。D1 双向验收两个方向都过；
> `schema eval` 在真图谱上跑出 1 条真硬错误（首版 5 条误报已收紧）；评估页浏览器实测通过；
> `schema data-quality` 四条探针只在内存 SQLite 上验证，**真库未跑**。
> 逐项交付说明见 [dev-checklist-2026-09](dev-checklist-2026-09.zh-CN.md) 各节。
