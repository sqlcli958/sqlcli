## 一、核心主张

当前产品最大的问题不是功能少，是**已建成的能力"不可见、不可测、不可信"**，
以及**用户拿到的是资料，不是答案**。

现在的用法是：Agent 检索到表和字段 → 自己拼 SQL → 我们提供的所有语义信息
（业务名、语义类型、值域、关系、血缘）都只是**参考资料**，
没有任何东西保证拼出来的 SQL 是对的。

下一阶段的转变应该是：

> ~~**让图谱从"资料库"变成"查询生成器"。**~~
>
> **2026-09-03 换成**：让 agent 拿到的上下文**不会骗它**。

~~价值主张从"我帮你找到表"变成"我给你一个大概率正确的查询"。~~
~~这是可用到好用的分水岭，也是本文两个方向的共同收敛点。~~

**换掉的理由是燃料。** 「查询生成器」的燃料是**人的口径知识**——实测三个工作区
metric 合计 **0 条**，需求侧空转；新主张（值域 / `grain` / 关系基数 / 数据质量 /
`schema eval`）的燃料是**库和代码本身**，不依赖任何人先写内容。
本文第一节剩下的判断——"已建成的能力不可见、不可测、不可信"——**没有变**，
而且"不可测"至今仍是空的。

## 二、方向 A：执行反哺图谱（建议优先做）

### 2.1 闭环断在哪

现在的循环：

```text
导入结构 → Agent 补语义（候选）→ 人评审发布 → Agent 检索 → 写 SQL → 执行 → ✗ 断了
```

执行结果没有任何东西流回图谱。图谱的增长完全依赖人和 Agent 手工维护，
用得再多也不会自己变准。

### 2.2 关键洞察：scan-sql 的死因在这一侧不存在

`schema scan-sql` 当初被删除，是因为对主目标文件类型（MyBatis Mapper）
**解析失败率 100%**——动态 SQL（`<if>` / `<foreach>` / `${}`）是静态解析的
结构性盲区（见 [product-plan-2026-08](archive/product-plan-2026-08.zh-CN.md) 1.2 节）。

**但执行日志里的 SQL 是渲染完成后的静态 SQL，那个盲区在这一侧根本不存在。**

同一个目标（自动发现 JOIN 关系），换一个数据源，就从"结构上不可能"
变成"几乎免费"。

### 2.3 现成的数据：`sql_execution` 全量躺着，无人挖掘

```sql
CREATE TABLE sql_execution (
  id, alias, sql_type,
  masked_sql    TEXT NOT NULL,   -- 脱敏版，任何时候可展示
  raw_sql       TEXT,            -- 逐字原文 ← 挖掘对象
  status, error_summary, affected_rows, elapsed_ms, started_at,
  source, rerun_of
)
```

现状核实：`raw_sql` 只被写入、以及读回来做展示与重放，
**全仓没有任何分析/挖掘代码**。

### 2.4 能挖出什么

| 挖掘对象 | 产出 | 替代了什么 |
|---|---|---|
| `JOIN ... ON` 子句 | `join_observed` 候选关系（走现有候选评审流程） | **补上 scan-sql 死后留下的洞** |
| 表/列访问频次 | 自动 `boost` 初值 | 现在 boost 是纯手工盲调，用户改完不知道效果；热度是天然先验 |
| `WHERE` 谓词字面量 | 值域补全候选 | `WHERE status = 2` 高频出现而 `enumValues` 里没有 `2` → 标注不全 |
| 失败/零行的执行 | 语义标注质量信号 | 哪些表的查询经常报错，指向标注错误 |

### 2.5 风险与约束（必须一起设计，不是加注意事项）

1. **幸存者偏差**：只能学到已经有人查过的 JOIN，发现不了没人查过的关系。
   → 定位为"补充发现"，不能当作关系完备性的来源。
2. **烂 SQL 也会被挖进来**：错误的 JOIN 一样会被记录。
   → 按 **出现频次 × 执行成功率** 加权，低于阈值不产出候选。
3. **一律进候选区，绝不直接生效**。这套机制（candidate → 人评审 → 发布）
   已经建好，直接复用，不要为自动挖掘开后门。
4. **脱敏边界**：挖掘用 `raw_sql`，但产出的证据（`RelationEvidence.sourceRef`）
   里不能带回字面量值。谓词挖掘只取"列 = 某常量"的**列和常量的形状**，
   敏感列（`SemanticType` 属敏感信息组）直接跳过。

### 2.6 ~~为什么建议它排第一~~ → **改判：它排不了第一，因为燃料还不存在**

> **2026-08-25 修订。** 原判断说"数据已经在 SQLite 里，成本最低"——成本判断没错，
> **但没有人去数那份数据有多少**。数完之后结论反过来了。

实测 `~/.sql-cli/sqlcli.db`：

| 指标 | 实测值 |
|---|---|
| `sql_execution` 总行数 | 302 |
| **其中含 `JOIN` 的** | **42** |
| source 分布 | `normal` 238 · `migrated` 41 · `ui_workbench` 15 · `ui_rerun` 8 |
| 对照：图谱规模 | 499 表 / 9727 字段 / 65 关系 |

42 条 JOIN 语句，去重后大概率只剩十几个不同的表对，而且看 source 分布
**基本全是开发期自测与冒烟流量，不是真实分析流量**。

这让 2.5 节列的第一条风险（幸存者偏差）在当前语料规模下达到**最严重**的形态：
挖出来的不是"业务上常用的 JOIN"，而是**"我自己测试时敲过的 JOIN"**。
把它当候选喂进图谱，污染大于收益。

**更根本的问题是依赖方向搞反了。**

方向 A 是**流量的函数**——没有真实查询流量，它挖不出任何东西。
那么什么东西产生真实查询流量？是"用户能问出业务问题并拿到答案"，
而那正是方向 B 要做的事。

> **方向 A 是放大器，不是启动器。** 放大器必须接在已经有信号的地方。
> 现在的信号强度是 42 条自测 SQL。

它的价值判断没有变——闭环、自增长、补上 scan-sql 的洞，都成立。
**变的只是它该接在哪一步之后。**

## 三、方向 B：BI 语义层（不是 BI 展示层）

### 3.1 先把两件事分开，结论完全相反

**BI 展示层（做图表）：不做。**

- Superset / Metabase / PowerBI 已经足够好
- 做图表需要巨额前端投入，而这不是本产品的优势
- [dev-checklist](dev-checklist-2026-08.zh-CN.md) 的"明确不做"当初就排除了 BI 图表，
  该判断至今成立

**BI 语义层（metric 定义 + 口径统一）：做，这是最自然的延伸。**

### 3.2 为什么是现在，为什么是我们

**LLM 时代语义层的消费者变了。** 传统 BI 语义层（LookML、dbt metrics、Cube）
是给**拖拽式报表工具**用的；今天最需要语义层的是 **Text-to-SQL 的 Agent**——
而本产品**本来就是给 Agent 用的**。

这是位置优势，不是跟风：别人的语义层要额外做一个 Agent 适配层，
我们的语义层天生长在 Agent 的工作路径上。

### 3.3 盘点：已有约 70% 的原料

| BI 语义层要件 | 现状 | 载体 |
|---|---|---|
| business glossary（术语 + 同义词） | ✅ | `TermWorkspaceNode`（含 `aliases` / `negativeAliases`） |
| join path resolution | ✅ | `schema path`（≤N 跳连通路径） |
| **dimension / measure 分类** | ✅ **隐含在 `SemanticType` 里** | `amount` / `quantity` 天然是 measure；`status` / `code` / `name` 天然是 dimension；`created_at` / `updated_at` 天然是时间维 |
| dimension 取值 | ✅ | `ColumnValueHints.enumValues`（带 `0=待付款` 口径） |
| 口径追溯 | ✅ | `LineageRecord`（字段血缘） |
| 检索 | ✅ | BM25 + CJK 分词 + boost |
| **metric 定义** | ❌ | **唯一的大缺口** |
| 聚合 / 时间粒度语义 | ❌ | |

`SemanticType` 那一行值得特别指出：它当初是为了敏感数据识别和展示而设计的，
但它**已经无意中完成了 measure/dimension 的初步分类**。这是一笔已付出、
未兑现的投入。

### 3.4 缺口就一样：指标口径的显式定义

```text
GMV = SUM(order.amount) WHERE status IN (2, 3)
                        ^^^^^^^^^^^^^^^^^^^^^^ 算不算退款？
```

这恰恰是企业里**最容易扯皮、最值钱**的那部分知识。
现在它散落在每个人的脑子里和一次性的 SQL 里，
而我们已经有了承载它所需的一切基础设施（候选评审、revision 乐观锁、
变更审计、血缘追溯）。

### 3.5 已决策：metric 是图谱工作区里的第四个集合

> **2026-08-25 拍板。** 原文把它写成"存图谱里 vs 独立一层"的二选一——
> **这个对立是假的**，`terms` 和 `lineage` 早就同时拿到了两边的好处。

`GraphWorkspace` 当前的实际结构：

```java
Map<String, SchemaWorkspaceNode> schemas;
Map<String, TableWorkspaceNode>  tables;
Map<String, TermWorkspaceNode>   terms;        // ← 不是边，独立集合
Map<String, LineageRecord>       lineage;      // ← 不是边，独立集合
List<RelationWorkspaceEdge>      relations;    // ← 只有这个是边
List<ChangeRecord>               changes;
List<ValidationIssueRecord>      validationIssues;
```

**"存哪里"和"长什么形状"是两个正交的问题**，原文把它们捆一起了：

- **存哪里** → 图谱工作区内。这样白拿 revision 乐观锁、候选状态、
  人工评审发布、`graph_change_log` 审计、export/import 载体，一样都不用重做
- **长什么形状** → 不是 `RelationWorkspaceEdge`，是独立的
  `Map<String, MetricRecord>`。原文四条判据里有三条支持这个结论
  （不是二元边、需要独立上下文、查询语义是展开成 SQL 片段而非图遍历）

所以答案是：**与 `terms` / `lineage` 平级的第四个集合，加在 `GraphWorkspace` 里。**
这不是新结构，是把已经用了两次的既有模式再用一次。

**别再把 metric 塞进 `RelationType`**——理由与"字段血缘不是关系类型"逐字相同。

### 3.6 `MetricRecord` 该装什么（最小可用形态）

只装"让 Agent 少猜一次"的东西，装不下的一律不装：

| 字段 | 为什么必须有 |
|---|---|
| `name` / `businessName` / `aliases[]` | 检索要能命中。**复用 `TermWorkspaceNode` 的同义词思路**，别另起一套 |
| `expression` | `SUM(order.amount)`——聚合函数 + 列引用 |
| `filters` | `status IN (2,3)`。**口径争议 90% 在这一行**，它是整个 metric 层的存在理由 |
| `grain` | 时间列是哪个 + 支持到什么粒度（`created_at`，`[day, week, month]`） |
| `dimensions[]` | 允许按哪些列切。取值直接走已有的 `ColumnValueHints.enumValues` |
| `joinPath` | **跨表时人工显式声明**，见下方那条注解 |
| `status` / `confidence` / `verified` / revision | 复用图谱既有字段，天然走候选评审流程 |

> **`joinPath` 是人工权威声明，不是自动发现的消费者——这一条把方向 A 和 B 的依赖关系倒过来了。**
>
> 原文 §4 的表格写着"metric 能算 ← 依赖方向 A 挖出的 `join_observed`"。这是错的。
> LookML 的 explore、Cube 的 join 都是**人手写的**，因为指标口径这种要扯皮的东西，
> 它的 JOIN 路径本来就必须是权威声明，不能是"从日志里猜出来的"。
>
> 反过来才对：**metric 里声明的 join 是全系统质量最高的 join 知识**，
> 它应该反哺给图谱，而不是等图谱喂它。

**明确不装**：物化 / 预聚合 / 调度 / metric store 存储层 / 指标血缘大图。
那些是 dbt、Cube 的赛道，进去就是第六节说的"滑向平台功能"。
判据不变：**不服务于"让 Agent 生成更正确的 SQL"的，不做。**

## 四、收敛点：`schema query-plan`

方向 A 和方向 B 看起来是两条线，实际收敛到同一个新能力上：

```text
输入：术语 / 指标 + 时间窗 + 维度
输出：
  · 涉及哪几张表
  · JOIN 路径（含 INNER / LEFT 判断）
  · 时间列是哪个
  · 敏感列需要 SM4 处理
  · 一个校验过的、可执行的 SQL 骨架
```

它同时依赖三件事，所以它是天然的收口动作：

| 依赖 | 来自 | 2026-08-25 修订 |
|---|---|---|
| JOIN 路径可信 | ~~方向 A 挖出的 `join_observed`~~ | **改：metric 里人工声明的 `joinPath`**（见 3.6 注解）。方向 A 是补充来源，不是前置条件 |
| JOIN 类型判断正确（INNER vs LEFT） | [ER 加强](graph-model-vs-er-model.zh-CN.md) 第 4.1 节的 optionality | 不变，但只对**自动推导**的路径才需要；metric 声明的路径自带 JOIN 类型 |
| 指标能算 | 方向 B（metric 定义层） | 不变 |
| 产出被执行后回流 | 方向 A（形成闭环） | 不变，但这是**结果**不是前提 |

**这一步才真正兑现"查询生成器"的主张。** 在此之前，我们做的都是让资料更好，
这一步开始做答案。

> **它必须和 metric 定义层同一批交付，不能排在后面。**
>
> 本文第一节的核心主张是"已建成的能力不可见、不可测、不可信"。
> 只交付 metric 定义而不交付消费它的东西，就是**再犯一次同一个病**——
> 又多了一份写完没人用的语义资料。metric 的价值 100% 在被展开成 SQL 的那一刻兑现。

## 五、建议顺序（2026-08-25 重排）

**原顺序把执行反哺排第一，已作废**，理由见 2.6：那一步的燃料实测只有 42 条自测 SQL。

新顺序的组织原则：**先做不依赖流量的，再做依赖流量的。**

> **2026-09-03：下面这三批整体暂停。** 第一批已交付但**零使用**（0 条 metric），
> 第二、三批的前置条件不再成立。现行顺序见
> [产品方向拍板记录](product-direction-2026-09-03.zh-CN.md) 第五节。
> metric 重新开放的信号：**出现一次真实的口径争议**——两次计算得出两个数且必须统一。
> 那一刻这份顺序原样恢复，因为它的内部论证没有被推翻。

```text
第一批（不依赖流量，现在就能做）        ← 已交付，零使用，入口已摘
  1. metric 定义层        GraphWorkspace 第四个集合 + CLI 写入 + UI 评审
  2. metric → SQL 骨架    必须与 1 同批交付，否则又是一份没人用的资料

第二批（第一批产生了真实流量之后）
  3. 执行反哺图谱          此时 sql_execution 里才有值得挖的东西
  4. optionality + 权威来源  提升自动推导路径的 JOIN 类型正确率

第三批（收口）
  5. schema query-plan     从「一个指标」扩展到「一个业务问题」
```

### 5.1 第一批的验收标准（只有一条）

> **一条真实指标，从人在 UI 里定义，到 Agent 用它生成出正确 SQL 并执行成功，端到端跑通一次。**

定义 20 条 metric 没有跑通 1 条有价值。第一批做完如果没人能演示这一条，
说明做的还是资料而不是答案。

> **2026-09-03 结算：这条验收从未达成**，实测三个工作区 metric 合计 0 条——
> 连 20 条都没有，更没有跑通 1 条。**这个验收标准本身是对的**，它准确地报出了
> 「第一批做完但价值没兑现」，只是没有人拿它去结算。
> 「换成按闭环验收」那条规矩（CLAUDE.md）就是从这里来的。

### 5.2 什么信号出现才开第二批

- `sql_execution` 里**由 metric 展开产生的**查询累计过百，且来自真实业务问题而非自测
- 或者：出现了 metric 声明里没覆盖、但被反复手写的 JOIN 组合

在那之前，方向 A 的代码一行都不用写——它的设计（2.4 挖掘对象、2.5 四条约束）
已经想清楚了，**想清楚但不动手，本身就是正确的动作。**

## 六、赛道边界：明确不做

- **图表可视化** —— 见 3.1
- **行级权限** —— 属团队版，触发条件未满足（见
  [团队版决策](sqlcli-team-edition-product-and-architecture-decisions.zh-CN.md)）
- **ER 建模 / DDL 正向工程** —— 见 [ER 文档](graph-model-vs-er-model.zh-CN.md) 第五节
- **不要滑向"又一个元数据管理平台"** ——
  DataHub / Amundsen / OpenMetadata 那条赛道已经很卷，
  而且它们是**给数据团队做治理**的。我们的差异化是
  **给 Agent 用 + 自带执行与审批闭环**，这两点它们都没有。

  一旦开始做血缘可视化大图、数据资产目录、owner 管理、数据分级打标
  这类"平台功能"，就进了别人的主场，而且丢掉了自己的优势。
  **判据：一个功能如果不服务于"让 Agent 生成更正确的 SQL"或
  "让人更快确认 Agent 的产出"，就不做。**
