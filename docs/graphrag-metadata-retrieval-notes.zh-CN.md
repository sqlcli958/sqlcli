# 从 RAG 到 GraphRAG：元数据检索实践阅读笔记

原文：<https://mp.weixin.qq.com/s/0M2Sd-vopmgnxhVd0fel5Q>

标题：从RAG到GraphRAG：货拉拉元数据检索应用实践

来源：微信公众号文章，本文档仅保留阅读摘要和对本项目的落地分析，不转载原文全文。

## 核心观点

文章讨论的是企业元数据检索场景下，从普通 RAG 升级到 GraphRAG 的实践路径。核心结论是：元数据检索的瓶颈通常不在大模型本身，而在知识组织和检索召回。表、字段、业务术语、同义词、血缘、口径说明之间存在天然关系，只靠向量相似度很难稳定命中，需要用图谱把实体和关系组织起来，再配合混合检索与重排。

文章中的实践结果显示，GraphRAG 方案相比 Naive RAG 有明显提升：整体准确率从 56% 提升到 78%，知识召回率、TopK 命中率和 MRR 也被作为关键评估指标。

## 对本项目的参考价值

当前项目已经具备 schema graph 的基础能力，包括 schema、table、column、relationship 的本地 JSON 建模，以及导入、查询、路径查找和 CLI 管理能力。这可以作为元数据 GraphRAG 的底座，但还不等于完整的元数据知识图谱。

文章对本项目最有参考价值的方向如下：

1. 将图谱模型从数据库结构图扩展为元数据知识图谱。

   当前模型主要表达库、表、字段、外键关系。后续应补充业务术语、缩写词、同义词、字段口径、数据血缘、常见问答、领域文档与表字段的关联。

2. 建立字段级索引，而不是只做整表级索引。

   整表作为检索 chunk 容易造成 token 超限和相似度误匹配。字段级 chunk 更适合“某个业务字段在哪张表能找到”这类问题。可以基于 `ColumnNode` 生成字段级索引文档，包含 `schema.table.column`、类型、字段描述、表描述、标签、业务术语和上下游关系。

3. 搜索能力需要从字符串匹配升级到混合检索。

   当前 `GraphQueryEngine.search()` 主要是表名、列名、描述的 substring 匹配。后续可以引入 BM25/全文检索、向量检索、标量过滤、图谱邻居扩展和 rerank，解决同义词、多实体、多关系和长尾查询召回问题。

4. 图查询需要支持反向关系和多跳推理。

   当前关系查询主要沿表上的出边遍历。元数据检索常见问题是“哪些表引用了这个实体”“某个业务对象相关字段在哪里”，这需要反向边、双向遍历、路径解释和可控的多跳扩展。

5. 需要实体权重和人工 boost。

   文章提到可根据表热度、下游数量、收藏、人工权重等指标计算表/字段分数。本项目目前所有表字段权重基本相同，容易把系统 schema、重复 schema、冷门表混入结果。可以给 `TableNode` 和 `ColumnNode` 增加热度、领域、人工 boost、重要性分数等属性。

6. 需要评估集和指标。

   表图谱相关代码当前缺少测试与评估。建议建立一组“找表/找字段/查口径/查关系”的问答样本，评估 TopK 命中率、召回率、MRR、路径解释正确性，再用 badcase 驱动图谱和检索策略迭代。

> **落地进度（2026-08-22 对账）**：下面「主要差距」一节写于图谱刚起步时，已部分过时。
> 现状：业务术语 + 同义词 + `term_mapping` 已有（第 1 点部分完成）；

## 与当前实现的主要差距

- 当前是 schema graph，不是完整 metadata knowledge graph。
- 当前数据源主要来自 JDBC metadata，缺少业务文档、数据血缘、术语库和人工知识。
- 当前搜索偏精确字符串匹配，缺少全文检索、向量检索和 rerank。
- 当前关系查询偏单向，反向引用和多跳推理能力不足。
- 当前没有表/字段重要性权重，也没有领域过滤。
- 当前没有表图谱相关测试、评估集和 badcase 分析流程。

## 建议落地路线

第一阶段：修正图谱底座。

- 修复 MySQL catalog/schema 抽取污染。
- 过滤系统库和无关 schema。
- 补齐反向关系查询。
- 修复路径 hops 计算和跨 schema 比较问题。
- 修复 schema CLI 参数解析。

第二阶段：扩展元数据模型。

- 新增术语、同义词、字段口径、数据血缘实体和关系。
- 给表、字段增加权重、热度、人工 boost、标签等属性。
- 支持从人工维护文件或元数据平台导入增强信息。

第三阶段：构建检索索引。

- 从图谱生成字段级检索文档。
- 建立表级、字段级、术语级索引。
- 先落地 BM25/全文检索，再接入 embedding 向量检索。

第四阶段：实现 GraphRAG 查询流程。

- 对用户问题做关键词、实体和业务术语识别。
- 使用同义词扩展查询。
- 通过混合检索拿到候选实体。
- 基于图谱扩展邻居、路径和上下游关系。
- 对候选表/字段重排，并生成可解释答案。

第五阶段：建立评估闭环。

- 沉淀常见找数问题作为评估集。
- 记录标准答案表、字段、口径和必要路径。
- 计算 TopK 命中率、召回率、MRR。
- 按 badcase 分类持续改进知识库和检索策略。

## 结论

这篇文章对本项目很有参考价值。当前项目已经具备表图谱的雏形，可以作为 GraphRAG 的结构化底座；但要真正支持自然语言元数据检索，还需要补齐业务知识层、检索索引层、权重重排层和评估闭环。
